# 缓存键携带每次写都变的版本计数（mlen）——写读交织下缓存归零，每读全量重建

## 问题描述

dom-ops 基准 `geom.write_read.thrash`（写样式→读 gBCR 交替）ZeroWeb ~12.4ms/op vs Chrome ~1.4µs（比值 ~10079x）。探针 bisect 排除 setup 清理、timer 间隙、脏元素数、队列长度增长、前序子场景、机器负载后，锁定在读路径缓存键设计：`RECT_LAYOUT_CACHE` 键为 `(html, drain_gen, mlen, vw, vh)`，`mlen` 是 pending mutation 队列长度——每次样式写追加一条 mutation，键必然变化。

## 根因分析

写读交织正是该缓存要服务的负载，但键含 mlen 使每次写都换键：单槽缓存命中率归零，每次读走全量重建（`with_cached_document_styles_lazy` 的 parse+cascade 代际缓存键同样含 mlen → 同样 miss；`LayoutEngine::compute` 整文档布局 + HitTest 填表 + HashMap 克隆）。600 cell fixture 实测 ~13ms/op，且成本与队列长度无关（300 op 队列 2→600 条全程平坦——是固定重建成本，不是按队列长度线性 replay）。量级自洽：13ms ≈ 2× 引擎直连管线分相（parse 0.38 + style 1.12 + layout 4.35 = 5.85ms）。同键第二次读起确实 O(1)（0-30µs）——缓存在「读读」负载下有效，「写读」负载下失效。

通用模式：**缓存键任何分量若在「被缓存结果的正常使用循环」内必然变化，该缓存对该负载等效不存在**，且因重建成本被单槽结构放大为每读一次全量。版本计数进键正确的前提是版本按「批量提交」推进（如 drain_gen 按 drain 推进），而非按每次写推进。

## 解决方案

M3 未改此键（缺陷1 语义修复优先且已正确）；优化方向 = 键改用「失效代际」（按脏范围/批量提交推进）或增量布局（脏元素范围重算）。已按目标契约转入专用性能工作流（见 docs/goal/dom-operation-bench/evidence/2026-11-04-m3-hotspot-attribution/）。

## 如何避免

- 给「读路径加速」缓存定键时，先写出目标负载的访问序列（本例：写、读、写、读……），逐项检查键分量在序列中是否稳定；键分量在目标负载内必然变化 = 缓存对该负载无效。
- 判别「固定重建 vs 线性 replay」：对 per-op 成本做增长剖面（长序列逐 op 计时分桶取中位）——平坦即固定成本，与队列长度无关；这决定优化方向是「降低单次重建成本」还是「避免随状态增长的重放」。
- 单槽缓存 + 全量重建的组合会把「偶尔失效」放大成「每次读都全量」——多槽或按内容分片能让部分命中存在。
