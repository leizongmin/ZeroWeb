# ViewPainted 积压帧合并

**日期**：2026-08-08

**相关模块**：`zero-browser`、`zero-renderer`、`zero-protocol`

## 问题描述

较大页面分阶段加载时，renderer 会连续发布完整 `ViewPainted`。browser 虽然为 IPC poll 设置了 4ms 预算，但仍会在 UI 线程逐帧把完整 IPC 快照转换为渲染图元、重建命中测试树并更新页面快照。页面越大，中间帧的重复成本越高，窗口事件处理越容易延迟；此时总 CPU 不一定高，因为瓶颈集中在 UI 主线程的串行工作。

## 根因分析

进程隔离只把 DOM、样式、布局和页面绘制生成移到了 renderer。最终页面图元仍需由 browser UI 线程接收并合成。

原有 4ms 预算只在两条 IPC 消息之间检查时间，不能中断单个大帧的 O(P) 转换，也不会淘汰已经过时的中间绘制帧。因此积压 N 个完整帧时，UI 线程会重复执行 N 次快照转换，即使最终只有最后一帧会显示。

## 解决方案

browser 每次 poll 仍按顺序处理 Fetch、Storage、标题、加载状态和事件回执，但对同一 renderer 的 `ViewPainted` 只保留本轮最后一帧。消息队列排空或达到预算后，仅把该最新帧提交到 `TabSnapshot`。

该策略不改变最终画面和控制消息语义，将一轮 poll 的完整快照转换次数从积压帧数 N 降为 1。单个大帧仍是 O(P)，后续若继续成为瓶颈，应把 IPC 快照转换移出 UI 线程，或让 compositor 直接消费 renderer display list。

## 如何避免

+ 高频生产、低频消费的全量状态消息必须采用 latest-wins 合并，不能按事件日志逐条回放。
+ 时间预算必须检查单项工作的最坏耗时；只在任务边界检查无法约束超大单项任务。
+ 评估多进程性能时要分别检查计算隔离和最终消费线程，不能只看 renderer 是否独立。
