# reftest「可疑 case 审计列表」是尾部截断子集，行为零变化判定必须比对全量失败集

## 问题描述

T61 F1 批次判定「行为零变化」时依赖 runner stderr 里的
`可疑（近纯色）case 审计列表（前 20）`。该列表只列 `suspicious_ids` 的前 20 条
（DC-14 退化假绿审计用途），不是全量失败清单。批次结束后对比两轮输出，发现
Total/Failed 计数净 +1（5110→5111），但审计列表肉眼比对无新增——多出的那例
失败 case 根本不在前 20 条里，差异被列表截断掩盖。

## 根因分析

`tests/wpt-runner/src/main.rs` 的审计列表输出为
`suspicious_ids.iter().take(20)`（DC-14 注明只供人工审计，不参与通过判定）。
它天然是子集：总失败数超过 20 或新增失败排在列表尾部之外时，两轮列表的
差集为空而真实失败集已经不同。把「审计列表无新增」当「行为零变化」的证据，
判定依据就从全量退化为采样。

## 解决方案

行为零变化判定只以全量失败集为准：比较两轮结果 JSON 的失败 id 集合
（`results[].id` where `!passed`），审计列表仅作可疑 case 的人工入口。
集合出现净增/净减时，对差异 case 单独 `--exact`（或等价 filter）连跑 3 次
判稳：3/3 同向才定性为真实变化，否则按 flake 记录不阻塞批次。T61 F1 的
净 +1 case 即按此流程复判为 flake，批次结论保持零变化。
