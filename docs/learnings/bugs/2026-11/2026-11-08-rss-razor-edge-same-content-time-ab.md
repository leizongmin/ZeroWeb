# 归因批须断言现行门禁腿定义：腿定义漂移使 5 次重载 bisect 答了已废弃的问题

## 问题描述

2026-11-08 F3 插入 caret 刀归因批中，午后 5 次 solo 归因腿（full-main、R5460-revert、append-revert、viv-off、v3eq 五种内容）全部被内存守卫杀（峰值 4.21-4.64GB，超 4GB/进程线 18.6-449MB），而同日晨间 v3 门禁 3 连过。事后对账发现：solo 腿模板跑的是 `testharness-editing-run zz-probe`（全家 76 页单进程），11:22 勘误后的门禁 probe 腿是 `testharness-editing-run-one FILTER=zz-probe-knife11-v2`（单页 241 行）。5 次重载 bisect 测的是**门禁早已不用的旧腿定义**，其杀与门禁可行性无关；门禁单页腿全天未被杀过。

## 根因分析

两层叠加：

1. **腿定义漂移无断言**：门禁腿定义从全家改为单页（勘误 11:22），solo 归因模板未同步。归因批与被归因的门禁批跑不同工作负载时，结论不可迁移——重载工作负载（76 页累积 RSS 基底≥4.2GB）的杀不代表门禁腿（单页）会杀。
2. **工作负载容量与内容无关性误读**：家族单进程峰值在 5 种内容变体下全部超线（min 4.213GB），429MB 离散度主要来自环境噪声（负载波动、兄弟流满核），但基底本身已超线——这不是"内容剃刀边"，是"工作负载容量事实"。把重载工作负载的贴线杀当内容信号，会逐个错杀无辜 commit。

## 解决方案

1. **归因腿定义断言**：归因/bisect 批发射前，把受试腿命令行与现行门禁批脚本逐字对账（FILTER、`-one` 与否、TIME_LIMIT）；门禁腿定义勘误后，在飞归因批作废重对。
2. **跨负载结论禁迁**：A 负载的杀/过不能外推到 B 负载；"同内容跨时段 A/B"必须同命令行才算 A/B。
3. **容量事实与内容归因分账**：工作负载基底超线（5/5 杀，min 超 0.44%）先记为容量事实；跨内容变体超线幅度离散（此处 429MB）在基底已超线时对内容归因无信息量。
4. **不改守卫换绿**：容量问题不得调守卫阈值解决（改守卫配置换绿灯=禁令）；出路是语料分片/降载或窗口纪律，属控制面决策。
