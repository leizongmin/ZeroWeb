# 批脚本 md5 守卫快照须落构建后，脚本起点快照会误标二进制身份

## 问题描述

fbq 轮 legs5 批（`batch-fbq-legs.sh`）的 shim md5 混合二进制守卫在**脚本起点**快照（`md5sum part01*.js part06.js | md5sum`）。脚本 04:20:38 启动，快照记录 51c49ed8；04:23:43 七个 shim 文件编辑落盘；fb 腿 make 04:25 才执行构建——构建读取的是编辑后内容，但账面 md5 仍是启动时旧树。事后两批（legs5 记 51c49ed8、mt2 记 59791ef5）md5 不一致，引发「两腿二进制是否同一内容」的错判：并行判读据「构建窗 04:21:10 收口 + md5 不同」误推 legs5 二进制不含 04:23:43 两笔修复，而实测 legs5 fb 二进制含修复（修复面行复绿实证）。

## 根因分析

守卫快照时点与构建时点脱钩：快照在脚本起点，构建在腿级 make（启动后数分钟）。编辑落于「脚本启动→构建」窗时，快照既不代表构建输入，也不能用于跨批比对。md5 一致性守卫的语义是「锚定二进制内容身份」，锚点必须在构建事件上，而不是批事件上。

## 解决方案

快照移到 build 完成之后（build 前后各一次更佳：前者记录输入、后者锚定身份；跨腿与跨批比对一律用 build 后值）。判读侧的对账要点：批账面 md5 不同时，先核各批快照时点与源文件 mtime 序，再下「二进制不同」结论；修复面行为行（该修复针对的语料行是否复绿）是比 md5 更直接的二进制身份证据。
