# 控制面挂账失败族开工前先核窗界分布，签名 A 跨窗伪影会伪装成引擎债

## 问题描述

editing 语料按断言粒度窗切（?1-1000 / ?1001-2000 / ?2001-last）跑批，控制面「下一步①」把读面挂账族记为 ×5 + ×2（同型嵌套 ×5 + 其他 ×2），照单开工。逐行窗界核对后定谳：7 行挂账里只有 4 行真债（iol `:448`/`:478` + iul `:233`/`:263`），iol `:393` 与 iul `:428` 是签名 A 跨窗伪影——该行断言块恰好横跨窗界，exec 在前窗跑过，后窗重跑到 after-reads 时对未动的 setup 树直读，恒假红，非引擎可修（sr2 轮已有同签名先例）。若照单全收做引擎刀，两行永远不会翻绿，白付一轮门禁且留下无法收敛的账面。

## 根因

控制面挂账来自跑批 Fail 行聚族归因，聚族时只按失败断言形状（qState-after 假红）分族，没有核对每行所属窗口与断言块是否跨界。签名 A 的可观察指纹：同一形状的 dps-p 变体在单窗内全绿 + 失败行的 Pass 断言子集与 Fail 断言子集分属两窗 + after-reads 读到的树与 setup 期望树逐字相同（exec 未曾在该窗执行）。

## 解决方案

- 开工前对挂账族逐行跑窗界分布核对：行号/断言序号落在哪个窗、断言块是否跨界、同形行在别窗或别的 runner 切片是否绿。
- 疑似伪影行用隔离探针直接验证引擎 in-window 行为：探针里让 exec 真跑，树与 qreads 若逐字合录音期望，则引擎无辜，行从债账除名（记伪影，不试图修）。
- 控制面挂账数字是开工输入而非验收目标；账面勘误（×5+×2 → ×4 真债）应随本轮落账回写控制面。相关：[探针判读必须覆盖全断言面](2026-11-06-probe-assert-full-row-family.md)——同轮两案合并纪律：判读前先定「哪行是引擎债、哪行是 harness 伪影」，再对引擎债行做全断言面判读。
