# 排空循环内重排队同通道命令：自馈送 100% CPU 永久自旋

## 问题描述

导航复位清队（ResetDocumentState）处理时，普通通道若滞留配置类命令（Shutdown/SetViewportHint/SetVideoPlayers 等），worker 以 100% CPU 永久自旋。单测实证：新回归测试首次构造出「Reset 处理时 cmd_rx 含 Shutdown」的序列，测试进程挂死 100% CPU 16 分钟。此前从未触发——所有既有测试与生产导航在 Reset 时普通通道恰为空，缺陷潜伏。

## 根因分析

清队臂的排空循环把需保留的配置命令用 `cmd_tx_purge.send(other)` 重排队，而 `cmd_tx_purge` 是**正在被排空的 cmd_rx 同通道**的克隆发送端：刚送回的命令立刻可被 `try_recv` 再次收到 → 再匹配 → 再重排队 → 无限循环。修复：循环内先收集到 `Vec`，循环结束后统一重发——重排队命令在 Reset 臂完成后的下一轮分派处理，语义不变。

## 解决方案

- 在 `try_recv` 排空循环体内向**同一通道** send 是自馈送模板——任何「边排空边保留」的逻辑都必须先收集后重发。
- 潜伏缺陷的暴露靠测试构造新命令序列：清队/取消语义的测试要覆盖「队列非空时触发复位」的组合，而不是只在空队列上验证。
- 测试挂死（100% CPU）先 ps 看进程态再定方位：自旋是纯 CPU，死锁是 0% CPU 等待——方向完全不同。
