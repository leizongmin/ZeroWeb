# roster/thd 漂移归因三板斧：逐名 diff → log -S 溯源 → is-ancestor 窗口归属

## 问题

任务门禁常要求「roster 红名册对基线逐名恒一」。实现分支跑出的 roster 与
基线不一致时，容易直接判交互回归；但基线轮与实现轮之间，main 常有并行
刀合入（分支切出点之后的 main 推进不进分支树，基线也可能在不同切出点算）。
不归因就下结论，会把并行引入的既有红算到本切片头上，或反过来把本切片
引入的真回归洗成「并行漂移」。

## 根因分析

漂移成员只有三种来源：本切片引入、并行刀引入（切出点后 main）、基线口径
错误（判读体/轮次间树不同）。三者必须逐一排除才能下「交互回归=0」的结论；
只有账面数字（P/F 总额）相同不足以证明逐名恒一，反之逐名相同也须核对
账总额防同额换名。

## 解决方案

三板斧（每步都要留命令与退出码）：

1. **逐名 diff**：`added = 实现轮 - 基线`、`removed = 基线 - 实现轮`，集合
   全列（不计数省略）。同时比对两轮 P/F 账总额；两轮自身先恒一才轮到跨轮比。
2. **溯源**：每个 added/removed 成员 `git log -S "<测试全路径或关键断言串>"
   --oneline` 找引入/消失提交；`--reverse` 看删除点。
3. **窗口归属**：`git merge-base --is-ancestor <引入提交> <分支基点>` 退出码
   0 → 并行窗口内（归属并行刀）；非 0 且引入提交在分支内 → 本切片引入。

**收敛判据**：removed=0 且 added 全部归属并行窗口、P/F 账与基线恒同，才可
写「交互回归=0」；任一 added 归属本切片提交即回归，按红处理不豁免。
基线必须在干净切出点实算（不沿用更早任务的账面值），否则第 3 步窗口归属
失去锚点。

**Why**：门禁结论的可信度来自归因链而非账面巧合。三板斧把「数字对上了」
升级为「每个成员都对得上来源」，防止并行噪声与真回归互相冒名。

**How to apply**：roster/thd 类门禁脚本里内置 judge 段（如 t71-after-roster.sh
的 python 抽取段），断言 added/removed 双空并输出逐名清单；发现漂移时按
三板斧出归因附记，结论写进任务 op-result，不在 commit message 里省略过程。
