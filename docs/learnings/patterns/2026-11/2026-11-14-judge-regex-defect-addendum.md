# 集成 judge 正则盲区误报时改编译判读产物为独立附记，不改编证据原件

## 问题

集成 judge（如 reftest-judge、repro-judge 的 python 判读体）输出是证据原件。
当正则存在盲区（如按行首缩进抽失败名漏掉带修饰行、按固定分隔符切字段遇
格式漂移），judge 会误报漂移或漏报成员。直觉修法是改判读体再重跑——但
历史轮次的证据原件都是旧判读体产的，改编读体后新原件与旧原件不同源，
跨轮比对（逐名恒一等硬门）失去同一判读基。

## 根因分析

证据原件的权威性来自「产生它的判读体 + 产生时刻的树状态」二元组。改判读
体等于换尺子：新旧测量不可直接比。正确做法是把尺子的缺陷修正作为**独立
附记**与原件并列：原件不动，附记记录（a）正则缺陷是什么、（b）用修正后
口径对同一原件重算的结果、（c）重算与原件口径的差异逐名清单及溯源。

## 解决方案

附记落证四步（T70 reftest-judge-addendum 形制）：

1. **逐名 diff**：修正口径 vs 原件口径的成员集合 diff（added/removed 各自
   列全名，不省略）。
2. **溯源引入提交**：对每个 diff 成员 `git log -S "<判读体中该成员的匹配
   关键串>"` 找到引入/消失提交。
3. **窗口归属实证**：`git merge-base --is-ancestor <引入提交> <窗口两端>`
   证明该成员的引入在受影响窗口内（还是窗口外并行刀带入的无关漂移）。
4. **对端窗口零贡献核验**：证明对面臂（chrome/base 侧）在窗口内 docs-only
   或零改动，排除「对面也变导致 diff」的假象。

gate 结果引用附记（judge 行 + addendum 行并列），不替换 judge 原行。

**Why**：判读产物是审计链的地基。修尺子不重标旧数据，等于让跨轮硬门
（逐名恒一）在两个口径间偷换概念；独立附记保住「原件不动 + 修正可验」
两件事同时成立。

**How to apply**：发现 judge 输出可疑时，先抽一名手工核对判读体正则
（`grep -E` 复算单名），确证盲区后按四步落附记文件；gate 记录写
`judge: <原值> + addendum: <修正值>`；附记引用的每条溯源都要带命令与
退出码，不写结论性断言。
