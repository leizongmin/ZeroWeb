# 无 perf/gdb/Profiler 下定位 js worker 饱和的方法阶梯（bilibili 输入卡死案）

## 问题

真站（bilibili）搜索框点击后页面冻结数十秒：键入无回显，renderer 内 js 线程接近满核。当时 ZeroWeb 无 CDP Profiler 域实现、无 V8 --prof 管道、无法 gdb 附着（会冻结进程破坏复现），缺乏现成的 JS 侧热点工具。

## 方法阶梯（由粗到细，每步都能独立排除一半假设）

1. **线程级 CPU 归因**：对 renderer 进程做 `/proc/<pid>/task/*/stat` 采样（或 `top -H -p`），把「renderer 满核」分解到线程名——`js worker`（脚本执行）与 `renderer-runtim`（样式/布局）燃烧比例决定往脚本侧还是样式侧走。本案两者同时高，说明脚本在**高频驱动**样式失效，而非布局自身死循环。
2. **合成最小复现剥离站点**：用无站点依赖的静态页 + 定时器复刻可疑 API 形态（本案：深层 DOM 小写页 + 40Hz `getComputedStyle` 逐属性读）。复现成功 → 站点特判排除，进入引擎内部归因；失败 → 回到事件/导航路径另查。
3. **桥级延迟测量**：在可疑桥调用两端打点，分离 cached 与 miss 形态。本案 `getComputedStyle` 单属性读 cached 0.01ms vs miss 247-262ms——量级差直接钉死「缓存失效粒度」为主成本，而非 cascade 单次过慢。
4. **代际键守恒审计**：列出缓存失效的全部代际键（html 快照 / drain 代数 / style 版本），对一次用户操作逐键记录谁在变。任一键翻转即全量重算的设计下，「哪条高频路径在翻键」就是优化靶点。
5. **目标形态对照**：同一 API 调用频率下，leaf 目标 vs body 目标对照（本案 js 线程 2.5% vs ~92%）——分离「单次调用成本」与「变更子树规模主导的 cascade 成本」两个正交因素。

## 结论与产出

该方法阶梯把「全文档重排风暴」归因收敛到 **gCS 代际缓存换代粒度**（任一代际键变化即全量重算，增量分支永不触发），修复以三级换代 + drain 记录同步交付（PR #88）；真站 journey 的残余卡顿归因为另一来源（异步 API 轮询周期成本，独立任务 t7）。

## 适用边界

- 适用于「CPU 饱和 + 页面存活（可恢复）」形态；硬死锁/崩溃形态第 1 步之后即需转向阻塞点采样。
- 步骤 3-4 需要能在引擎内临时打点（诊断性修改，验证后还原，不进提交）。
- 精确到函数级的周期成本分解（t7 需要的「每次轮询花在哪」）仍缺工具：CDP Profiler 域实现 / V8 --prof 管道是解除该缺口的候选使能项。
