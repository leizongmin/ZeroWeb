# coverage 面级 0P 断层的提交窗口二分法

## 问题描述

wptfyi 快照某个面（如 form-url-encoding ~112 万子测试）整面 0P，需在
无现成单测复现路径时定位引入提交。难点：肇事提交往往与该面**看似无关**
——本例 form 面 0P 由 T26 Cache API 提交（`60ce14698`）经 host 桥副作用
造成，按面路径过滤 git log 完全漏报。

## 根因分析

面级 0P 的来源空间远大于该面的直接修改：任何改到共享路径（execute_script
入口、探测环、harness 注入）的提交都可能整面打挂。所以「找相关提交」
思路不可用，必须按时间窗暴力二分。

两个易错点：

- **窗口设错**：两次快照日期之间的提交不是相邻两个——本例窗口内实际有
  71 个提交，首二分误按相邻提交设窗把结论带偏。先 `git rev-list` 数清
  窗口内提交数再取中点。
- **只证相关不证因果**：二分收敛到单提交后仍需改前/改后 A/B 验证因果，
  并排除与快照分母/口径变化（语料版本、runner 逻辑）的耦合。

## 解决方案

流程（本轮 7 轮收敛单提交）：

1. 锁定面从健康到 0P 的时间窗（两次快照日期），`git rev-list` 列全窗口
   提交并数清数量。
2. 每轮：checkout 中点 → 守卫构建（systemd-run 限内存墙钟）→ 跑该面
   **单页**（选子测试最多的代表页，如 errors-han 24 entries 23,097 子测试，
   健康时 1-3 分钟）→ PASS/STALL 裁决 → 收缩窗口。二分脚本固定化
   （checkout/build/run/裁决一体），避免每轮手拼。
3. 收敛到单提交后，用打点法确认因果链（见对应 bugs 学习：
   探测环 state + 页面旗标读回），再做修复。
4. CI 侧证据只作定位起点；复现一律落本地单页，分钟级反馈远快于
   3.5h 的 CI 轮。

适用边界：面级「整族 0P / 通过数断崖」这类聚合口径异常；单点失败直接
看失败清单即可，不值得二分。
