# 后台轮询与窗口重绘解耦

**日期**：2026-08-08

**相关模块**：`zero-host-runtime`、`zero-browser`

## 问题描述

browser 通过后台线程完成网络请求，并通过 channel 接收 renderer IPC。若 winit 事件循环完全休眠，后台结果不会被消费；若用连续 `request_redraw` 保持循环活跃，主进程会持续执行完整 UI 合成，现场 CPU 可升至约 86%。

## 根因分析

“需要轮询后台状态”和“窗口内容需要重绘”是两个不同信号。将前者映射为 `RedrawRequested` 会让没有视觉变化的等待阶段也执行 GPU/CPU 合成。

## 解决方案

HostRuntime 增加不触发绘制的 `AppEvent::Poll`。ZeroBrowser 以 16ms 间隔执行非阻塞 IPC/网络轮询；只有实际收到新快照或 UI 状态变化时，现有 `needs_redraw` 路径才请求一次重绘。

现场验证：

+ 页面资源和后续脚本请求持续推进，不依赖鼠标或窗口事件唤醒；
+ 加载稳定后 browser 约 0.3% CPU；
+ 加载稳定后 renderer 约 0.0% CPU。

## 如何避免

+ 后台任务完成通知不得复用高成本绘制事件。
+ 事件循环必须区分“推进状态机”和“提交新画面”。
+ 性能修复后要复测异步任务能否继续推进，防止旧空转意外承担了唤醒职责。
