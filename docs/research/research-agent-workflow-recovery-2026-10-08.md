# 长任务压缩后的流程恢复与交付门禁

日期：2026-10-08。对象：`.agents/skills/zeroweb-site-optimizer`。本地依据版本：`678cf523e7721597e554af3eb33a5c1a641d0b07`。

本次核对 Skill、交付检查器与官方工程资料，提出方案；未修改 Skill，未审计具体历史 PR 或宿主轨迹，未验证 TRAE 的压缩回调能力。

## 结论与范围

建议把每次压缩视为一次执行者恢复：从磁盘恢复事实，按阶段重新加载规则，并在发布、合并前检查必需证据。这样即使摘要漏掉细节，也能重新取得原始要求；遗漏关键步骤时，交付入口能阻止继续。

优先补三处：限定“已读文件”的有效范围；让 PR 正文和双审查完整性进入可执行检查；把检查接到实际动作入口。现有 workflow、checkpoint、operation、manifest 已经提供状态和版本基础，无需另建一套总账。

完整循环建议为：读取运行指针，核对磁盘与远端事实，装载当前阶段规则，执行一项有界任务，验证产物，保存回执，再推进阶段。

本次问题映射到三个工程主题：长程 Agent 执行环境（agent harness）、压缩后的上下文重建（context rehydration）、可恢复工作流（durable execution）。范围仅涉及持续数天的网站优化中的流程遗漏、PR 交付和审查可见性，不扩展到浏览器产品修复或更换 Agent 平台。

## 业界依据及适用边界

Anthropic 的长程 Agent 实践明确指出，压缩本身不足以保证多上下文任务完成；其做法包含结构化任务清单、进度文件、每次新会话重新建立任务状态、逐项推进和真实验证。[8] 这支持复用本项目已有账本，并明确每次恢复的装载流程。

Claude Code 官方文档直接提供 `SessionStart` 配合 `compact` matcher，在压缩后重新注入关键内容；`PreToolUse` 可以在动作前执行校验并阻止调用。[9] 前者解决内容重新可见，后者解决遗漏要求仍执行动作。它们是 Claude Code 的能力示例，不能把相同配置直接当成 TRAE 可用方案。

OpenAI 的工程文章采用短入口导航到仓库中的正式知识，并用 linter、结构测试等机制强制执行部分不变量。[10] 对这里的启示是保留短而稳定的恢复入口，详细要求按阶段读取，能客观判定的交付条件进入工具检查。

LangGraph 的持久执行文档要求保存执行状态，对副作用采用任务封装与幂等设计；恢复时可能重放步骤，不能假定从中断行继续。[11] 本项目已有 operation 意图和远端查重要求，应保留“先确认已产生的效果，再补缺失动作”，避免因压缩重复创建 PR 或合并。

Anthropic 2026 年的文章讨论实现者与评价者分离，以及结构化交接。[12] 同文也指出，早期某模型需要显式上下文重置，后续使用 Opus 4.5 的实验又移除了重置。因此不能把“每个任务强制清空主控上下文”当作普遍最佳实践；可以先沿用本项目已有的新 worker/reviewer，在实测中决定主控重置频率。

OpenAI 的案例还采用较少的阻塞合并门，[10] 这是特定产品对吞吐量与纠错成本的取舍。本项目已有明确交付约定，本文只借鉴可执行约束和知识管理，不据此削弱双审查或合并条件。

## 建议的最小改进

### 压缩后按阶段重新装载

建议将入口的缓存规则改为：“仅当前上下文中仍可见、且版本未变的内容可复用；压缩、交接、新会话后，重新读取入口和当前阶段必需文档。摘要中的‘已读’不能代替正文。”

在宿主保证会注入的短入口中，保存运行目录的定位方式和恢复动作。恢复包从 workflow/checkpoint 生成，只包含当前 task、stage、repo/PR、精确 head/base、未决 operation、授权引用、原 deadline、下一动作及必读路径。规则正文继续单点维护，不另存一份手写规则摘要。记录规则版本或摘要，避免任务期间规则变化后无意混用；规则变化也不能自动扩大原授权。

| 即将执行的动作 | 应重新装载的材料 |
|---|---|
| 恢复当前任务 | SKILL 入口、原合约、workflow/checkpoint 和未决操作 |
| 创建或更新 PR | github-delivery、github-pr 模板、当前证据映射 |
| 派发首轮审查或复核 | independent-review、精确受审版本、该角色输入包 |
| 合并与集成 | github-delivery 的合并规则、当前汇总回执、远端状态 |

每次阶段切换都执行这套装载，即使没有收到压缩事件。宿主支持压缩回调时，再自动注入恢复包。把“请记住重新读取”只写在可能被遗忘的 Skill 深处，仍存在同样问题。

### PR 交付从模板生成，并校验远端结果

复用当前模板，以结构化场景证据生成正文骨架；Agent 填写原因、收益和限制。发布前检查章节、占位符、证据身份、截图适用性；发布后回读 GitHub 的实际正文，核验附件引用和版本。

附件完整性、图片可加载、展示前后是否正确是不同检查。脚本能验证 URL、摘要和数量，视觉语义仍需要实际查看及记录。截图不适用、用户禁止公开、能力缺失分别处理；不能为过门禁自动填写“不适用”。

创建 Draft 时允许如实记录缺口，附件不全不妨碍独立审查等可继续工作；标记交付就绪与合并时，才要求适用证据齐全。保留现有“PR 创建后双审查”的顺序，不能把双审查作为首次创建 PR 的前置条件，造成循环依赖。

### 双审查完整性进入机器检查，并对用户可见

扩展现有 `verify-delivery.mjs` 对汇总 artifacts 的解析。至少核验两类首轮角色、不同实际执行者、原始报告摘要、首轮相同受审身份、完成的 review operation，以及返修后的非作者复核与当前版本汇总。

旧首轮保留原 SHA；新 head 通过新增差异复核和受影响验证接续，不能为满足“身份一致”而篡改旧报告。适用范围遵循现有规则，保留纯拼写/排版等精确豁免。

执行者 ID 应能关联宿主实际派发和完成记录。两个不同字符串、`independent: true`、两份文件本身，都不能证明新上下文隔离。校验器验证可客观检查的关系；上下文输入隔离与审查质量仍需宿主记录及行为评测。

PR 正文新增简短的审查状态表，由报告自动生成：

| 审查环节 | 状态 | 受审版本 | 证据 |
|---|---|---|---|
| 测试有效性首轮 | 待执行 / 已完成 / 有缺口 | 原始 head | 报告引用 |
| 缺陷首轮 | 待执行 / 已完成 / 有发现 | 原始 head | 报告引用 |
| 返修复核及汇总 | 待执行 / PASS / CHANGES_REQUIRED | 当前 head | 汇总引用 |

同时显示未解决阻断项。公开部分只含允许公开的摘要和持久链接，不上传私有日志、内部会话轨迹；不能把本地文件路径当作远端证据链接。没有可公开报告时注明证据保留本地，用户可在本地运行报告查看。

### 把校验接入动作入口

仅在 Markdown 写“运行检查器”，或提供一个可选脚本，仍依赖 Agent 记得调用。建议增加薄的交付入口，调用既有检查器、保存操作意图、执行获准发布/合并、回读并保存结果；不重写浏览器控制或任务调度。

要把它变成强制门禁，需要宿主在工具动作前调用检查，或由受限工具/远端保护规则把持有写权限的路径收敛到该入口。仅用正则拦 `gh pr merge` 无法覆盖 `gh api`、其他 shell 写法、MCP 和浏览器操作。

GitHub 必需检查可以作为合并的另一层约束，但必须解决证据来源：本地 gitignored 运行目录不会自动出现在 CI。应由可信执行端提供最少必要、经脱敏的验证结果，不能让 CI 仅相信 PR 作者填写的“已审查”。正文修改不改变 head SHA，因此正文检查还需响应编辑事件或在合并前重新回读，避免旧检查继续显示通过。

缺少宿主强制能力时，先交付恢复包、阶段装载、生成器和检查器，明确其为降低遗漏的措施；不宣称可以完全防止绕过。当前尚未验证 TRAE 对应能力。

## 验证方式与实施顺序

先补恢复规则、阶段路由、PR 审查可见性，再扩展双审查及正文校验，最后核实并接入宿主/远端强制入口。全程复用已有运行目录和账本。

验收应观察工具调用与产物，不以 Agent 回答“我会遵守”判通过：

| 注入的故障 | 必须观察到的结果 |
|---|---|
| 摘要只写“修复完成，接下来创建 PR” | 自动恢复当前阶段要求，按模板形成正文 |
| 只有测试有效性报告，摘要却写“审查通过” | 缺陷首轮仍显示缺失，不能合并或记 done |
| 两类报告复用同一执行者 | 被完整性检查拒绝，不凭不同文件名通过 |
| 审查后 head 变化 | 旧报告保留，补当前差异复核和受影响验证 |
| 上传部分成功后压缩 | 回读正文，仅补缺失部分，不覆盖成功链接 |
| 合并返回未知后压缩 | 先查询服务端，不重复合并 |
| PR 正文删除截图，head 不变 | 正文检查失效或合并前拒绝放行 |
| 多次压缩后摘要丢失停止原因和预算 | 仍从原账本取得停止屏障及 deadline，不重置 |
| 摘要声称全部完成，磁盘仍有缺失证据 | 保持未就绪，输出具体缺项 |

确定性测试验证检查器是否拒绝错误输入；使用模拟工具的新上下文测试验证 Agent 是否真正走恢复和交付流程。另做真实宿主压缩测试，确认回调确实触发。运行新旧方案时保持输入、工具和模型条件一致，记录违规放行、重复副作用、无必要重跑、额外耗时及读取量，不预设提升比例。

质量检查：本报告区分了实际源码、用户观察与方案；保留模型差异和宿主能力限制；没有把历史独立审查写成已完成或未完成，也没有宣称建议已通过行为验证。
