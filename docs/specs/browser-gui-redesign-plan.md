# ZeroBrowser GUI 改造方案

> 状态：提议
> 范围：`apps/browser` 桌面 GUI 外壳，不含页面内核兼容性修复
> 关联模块：`apps/browser`、`crates/browser-shell`

## 1. 背景

`apps/browser` 已具备浏览器外壳的基础能力：

- 标签栏
- 地址栏
- 前进 / 后退 / 刷新 / 主页
- 自动补全
- 书签栏
- 查找栏
- 下载栏
- 状态提示
- 右键菜单

但当前实现仍更接近“可运行的自绘原型”，与主流桌面浏览器（Chrome / Edge / Safari / Firefox）相比，差距主要集中在：

- 信息架构不完整
- 视觉层级不成熟
- 控件质感和状态表达偏弱
- 平台整合度不足
- 一些辅助界面仍带明显工程样机感

本方案的目标不是立即追求“功能更多”，而是先把现有 GUI 从“能用”推进到“像一个成熟浏览器”。

## 2. 观察结论

以下判断基于当前源码和实际运行窗口：

- `apps/browser` 为自绘 GUI，不是套用现成 WebView 壳。
- 当前 UI 的主绘制和布局集中在 `app_render.rs`、`layout.rs`、`colors.rs`。
- `crates/browser-shell` 主要提供 UI-agnostic 的数据模型，适合继续作为状态层保留。
- 现有实现已经考虑跨平台差异，如 Wayland 自绘窗口控制、macOS unified titlebar 预留，但整体仍以功能接线为主，不是成熟产品级打磨。

## 3. 范围与非目标

### 3.1 本次方案覆盖

- 标签栏
- 工具栏
- 地址栏 / Omnibox
- 书签栏
- 查找栏
- 下载入口
- 悬浮状态提示
- 页面视口容器
- 窗口 chrome 与平台适配

### 3.2 本次方案不覆盖

- 页面内核兼容性问题
- 真实网页排版错误本身
- 浏览器进程模型调整
- 扩展系统、账号系统、同步系统
- 移动端 UI

说明：网页渲染异常会影响用户对 GUI 的整体观感，但本方案只处理浏览器壳层。

## 4. 设计目标

改造后的 ZeroBrowser GUI 应满足以下目标：

1. 第一眼看起来像成熟桌面浏览器，而不是工程演示。
2. 顶栏的信息架构完整，地址栏成为真正主入口，而不是普通输入框。
3. 浏览器壳弱化对内容的干扰，让网页内容成为视觉中心。
4. 标签、地址栏、菜单、状态反馈具备明确层级和一致节奏。
5. 保持现有自绘架构，不引入新的 UI 框架。
6. 修改尽量集中在 `apps/browser`，不破坏 `browser-shell` 的 UI-agnostic 边界。

## 5. 当前差距

### 5.1 顶栏信息架构过薄

当前顶栏偏向“导航控件 + URL 输入框”，缺少主流浏览器常见结构：

- 站点安全状态
- 页面动作入口
- 浏览器全局菜单
- 下载 / 收藏 / 权限等统一入口

结果是地址栏承担了输入职责，但没有形成浏览器主控件的认知。

### 5.2 视觉层级不稳定

当前标签栏、工具栏、页面容器之间的关系较硬，存在以下问题：

- 分层明显但不细腻
- 灰阶和边框对比偏生硬
- 页面视口像嵌在一张白卡中
- 地址栏视觉权重偏大但不够精致

### 5.3 标签体验偏原型化

虽然现有标签已经实现了类 Chrome 形状，但距离主流产品还差：

- 激活态与非激活态区分不够明确
- 状态种类少
- 多标签拥挤时的观感较弱
- 缺少 pinned、muted、crashed、attention 等状态语言

### 5.4 地址栏智能性和状态表达不足

当前地址栏更像“可输入 URL 的文本框”，不是成熟 omnibox：

- 左侧没有稳定的站点状态区
- 右侧没有统一动作区
- 自动补全层级偏弱
- URL、搜索词、建议类型之间的区分不够强

### 5.5 辅助界面风格不统一

书签栏、下载栏、查找栏、状态浮层、右键菜单各自可用，但整体像独立功能块，不像同一套产品语言。

### 5.6 平台整合度不够

当前已做平台适配，但仍停留在“能跑通”的层面：

- Windows 下标题栏和浏览器工具栏融合感不足
- macOS unified titlebar 仍偏布局预留，不够自然
- Linux / Wayland 的自绘边框偏功能补丁，不是高质量整合

## 6. 设计原则

### 6.1 简单优先

不引入新 UI 框架，不做大规模抽象重写。优先通过现有自绘体系完成升级。

### 6.2 内容优先

网页内容应成为主角。浏览器壳负责组织和反馈，而不是抢视觉中心。

### 6.3 顶栏优先

优先打磨标签栏、地址栏、菜单和窗口 chrome。这是用户最先感知的产品层。

### 6.4 统一节奏

统一图标尺寸、行高、留白、边框、圆角和 hover / active / disabled 状态，减少“每块都能用，但不是一套东西”的感觉。

### 6.5 状态可见

浏览器是高状态密度应用。加载、悬停、焦点、权限、下载、查找、标签状态都应有清晰反馈。

### 6.6 保持边界

- `crates/browser-shell` 继续负责状态模型
- `apps/browser` 继续负责 GUI 几何、绘制和输入
- 不把 GUI 细节反向侵入 `browser-shell`

## 7. 目标界面方向

建议首阶段对标 Chrome / Edge 的传统桌面浏览器结构，而不是直接追求 Arc 这类强重构 UI。

原因：

- 当前信息架构和交互基础更接近传统浏览器
- 传统浏览器模式更容易在现有代码上演进
- 先把成熟度做出来，再考虑差异化创新，风险更低

界面方向建议：

- 整体更轻、更稳、更克制
- 顶栏降低噪音，让地址栏成为视觉中心
- 页面内容区减轻卡片感
- 用少量明确的状态色，不依赖复杂动画

## 8. 分阶段改造方案

## Phase 1：顶栏重构

目标：解决“第一眼不像成熟浏览器”的问题。

### 8.1 标签栏

- 重整标签的高度、留白和文本截断节奏
- 强化激活标签与背景的连续关系
- 降低非激活标签存在感
- 为 favicon、loading、close 按钮建立统一布局槽位
- 预留 pinned / muted / crashed 状态位

### 8.2 地址栏

- 将地址栏从“输入框”升级为“主控件”
- 左侧加入站点状态区
- 中部保留输入 / 显示区
- 右侧预留收藏、页面动作、更多菜单入口
- 调整内边距、圆角、焦点态和选中态

### 8.3 导航按钮区

- 与地址栏统一垂直节奏
- 调整 disabled / hover / pressed 状态
- 让刷新、主页等按钮不再显得像单独漂浮图标

### 8.4 窗口 chrome

- Windows 下增强标题栏与工具栏融合
- macOS 下优化 traffic lights 预留区与标签布局关系
- Linux / Wayland 下将自绘边框收敛为低存在感辅助元素

### 8.5 产出

- 新的顶栏布局常量
- 新的配色节奏
- 新的标签与地址栏绘制逻辑

### 8.6 涉及文件

- `apps/browser/src/layout.rs`
- `apps/browser/src/colors.rs`
- `apps/browser/src/app_render.rs`
- `apps/browser/src/tab_chrome.rs`

## Phase 2：辅助界面统一

目标：让书签栏、自动补全、查找栏、下载入口、状态提示不再像拼装件。

### 8.7 自动补全下拉

- 增强建议行层级
- 突出主标题、次级 URL、来源标记
- 加强 hover / keyboard selection 表达
- 控制每行信息密度，减少拥挤感

### 8.8 书签栏

- 收紧高度与留白
- 图标与文本建立统一节奏
- hover 态与顶栏语言一致

### 8.9 查找栏

- 从“覆盖条”升级为更轻的浮动面板
- 强化匹配计数、结果跳转状态
- 避免与页面内容和滚动条争抢注意力

### 8.10 下载入口

- 首选从底部常驻条转向更轻量的面板式或角标式入口
- 保留下载进度信息，但减少页面底部被占用

### 8.11 悬浮状态提示

- 链接悬停状态栏继续保留，但更克制
- 统一圆角、阴影、文本大小和边距

### 8.12 右键菜单

- 强化分组和 hover 表达
- 后续可按上下文细化菜单内容，但首阶段先统一视觉语言

## Phase 3：内容容器减重

目标：让网页内容更像浏览器中心，而不是一张被包裹的卡片。

### 8.13 页面视口

- 弱化当前页面外框感
- 重新评估页面圆角、边框、底部留白与阴影
- 尽量让页面内容与浏览器 chrome 的关系更自然

### 8.14 滚动条

- 保持自绘，但与整体语言统一
- 减少厚重感
- hover / drag 状态更明确

### 8.15 状态叠层

- 保证查找栏、状态浮层、菜单、下载提示之间层级稳定
- 避免多个临时 UI 同时出现时界面显乱

## Phase 4：浏览器状态语言补全

目标：从“静态壳”进化为“有产品语言的浏览器”。

### 8.16 标签状态

逐步支持并绘制：

- pinned
- muted
- loading
- crashed
- attention

### 8.17 地址栏状态

逐步支持并绘制：

- secure / insecure / local / internal page
- loading
- permission / page action 占位

### 8.18 浏览器全局入口

- 增加“更多菜单”入口
- 收纳设置、历史、书签、关于等动作

说明：这一阶段会牵涉 `browser-shell` 的状态模型扩展，但应保持 UI-agnostic。

## 9. 建议执行顺序

建议按以下顺序推进：

1. Phase 1A：顶栏布局骨架重构
2. Phase 1B：顶栏视觉与控件状态收敛
3. Phase 2：自动补全与辅助界面统一
4. Phase 3：页面容器与滚动条减重
5. Phase 4：状态模型与状态语言补全
6. Phase 5：平台细节打磨

这个顺序不是按“代码最容易改”排的，而是按“用户感知收益最高、回归风险最可控、依赖关系最清晰”排的。

### 9.1 Phase 1A：顶栏布局骨架重构

先做：

- 标签栏几何
- 地址栏几何
- 导航按钮区几何
- 窗口 chrome 区域几何

本阶段只解决“结构和比例”，先不追求细节质感。

原因：

- 顶栏是用户第一眼最强感知区域
- 后续自动补全、书签栏、查找栏都依赖顶栏基线
- 如果先动辅助界面，后面顶栏再改会重复返工

完成标准：

- 顶栏整体比例稳定
- 标签、地址栏、导航按钮的对齐关系固定
- 相关常量和几何关系收敛到可维护状态

建议暂停点：

- 完成后先做一次实际窗口 review，不急着继续补功能状态

### 9.2 Phase 1B：顶栏视觉与控件状态收敛

在 1A 的骨架稳定后，再做：

- 配色节奏
- hover / active / focused / disabled 状态
- 标签激活态
- 地址栏焦点态
- 图标尺寸、留白、文本权重统一

原因：

- 没有稳定骨架之前做视觉细修，容易反复推翻
- 这一阶段能最快把“工程样机感”压下去

完成标准：

- 顶栏看起来像成熟浏览器，而不是 demo
- 控件状态一致，不再各画各的

### 9.3 Phase 2：自动补全与辅助界面统一

建议第二批处理：

- 自动补全 dropdown
- 书签栏
- 查找栏
- 状态浮层
- 右键菜单
- 下载入口

原因：

- 这些界面都依附顶栏和内容区边界
- 顶栏稳定后，再统一这些辅助层，返工最少
- 这一步能显著提升“产品完成度”

完成标准：

- 各辅助界面的圆角、留白、层级、状态语言统一
- 键盘与鼠标交互反馈清晰

### 9.4 Phase 3：页面容器与滚动条减重

建议第三批处理：

- 页面外框
- 页面圆角
- 页面边框
- 页面底部留白
- 滚动条视觉

原因：

- 页面容器的视觉权重会直接影响整体观感
- 但它依赖前两阶段先把 chrome 的上边界和浮层关系固定

完成标准：

- 内容区不再像厚重白卡
- 浏览器壳和网页内容关系更自然

### 9.5 Phase 4：状态模型与状态语言补全

建议第四批处理：

- pinned / muted / crashed / attention tab 状态
- secure / insecure / internal page 地址栏状态
- 页面动作入口
- 更多菜单入口

原因：

- 这一步往往会牵涉 `browser-shell` 的状态扩展
- 如果太早做，容易把不稳定的 GUI 细节带进状态模型设计
- 先把壳层布局打稳，再补状态，边界更清楚

完成标准：

- `browser-shell` 只增加 UI-agnostic 状态
- `apps/browser` 消费这些状态完成渲染

### 9.6 Phase 5：平台细节打磨

最后处理：

- Windows 标题栏融合
- macOS unified titlebar 细节
- Wayland / Linux 自绘边框存在感

原因：

- 这部分收益重要，但依赖前面主界面已经稳定
- 过早做平台细节，主布局一变就要重做

完成标准：

- 三个平台的差异处理不再像补丁，而像有意识的产品适配

### 9.7 不建议的顺序

不建议这样做：

- 先补更多按钮和功能入口，再回头重做顶栏
- 先做平台细节，再做主布局
- 先扩 `browser-shell` 状态模型，再确认 GUI 需要哪些状态

原因：

- 会放大返工
- 会把本来属于 GUI 细节的问题，过早固化成数据模型问题
- 很容易把任务做大，但用户观感提升有限

### 9.8 推荐里程碑

推荐把这轮改造拆成 3 个可评审里程碑：

1. M1：顶栏重构完成
2. M2：辅助界面统一完成
3. M3：内容容器减重 + 状态补全完成

每个里程碑结束都应做一次实际窗口 review，而不只看单元测试。

## 10. 建议拆分的执行任务

### Task A：顶栏视觉重构

目标：只改标签栏、导航区、地址栏、窗口 chrome。

验证：

- 1280x800 下整体更接近主流浏览器
- 顶栏不再显得松散和工程化

### Task B：自动补全与菜单视觉统一

目标：统一 dropdown / context menu / find bar / status bubble 的风格语言。

验证：

- 各辅助界面不再像独立组件
- 键盘和鼠标 hover 状态清晰

### Task C：页面容器与滚动条减重

目标：减少内容区卡片感。

验证：

- 页面与壳层关系更自然
- 状态浮层不会破坏内容视觉中心

### Task D：状态模型扩展

目标：为 pinned / muted / secure / menu actions 等状态补齐最小模型。

验证：

- `browser-shell` 状态扩展不携带 GUI 细节
- `apps/browser` 可消费这些状态进行绘制

## 11. 验收标准

改造完成后，应至少满足以下标准：

### 11.1 视觉

- 首屏顶栏看起来接近成熟桌面浏览器
- 标签栏、地址栏、页面视口层级清晰
- 各辅助界面的圆角、边框、留白、状态统一

### 11.2 交互

- 鼠标 hover、focus、pressed、disabled 状态明确
- 自动补全支持清晰的键盘选中反馈
- 临时 UI 叠层关系稳定

### 11.3 架构

- 不引入新的 GUI 框架
- `browser-shell` 继续保持 UI-agnostic
- `apps/browser` 的修改集中于绘制、布局、输入与状态消费

### 11.4 测试

建议补充或强化：

- 顶栏绘制快照测试
- 标签激活 / 非激活 / loading 状态测试
- 自动补全选中态测试
- 页面容器与状态浮层的渲染断言

说明：现有 `apps/browser/src/main.rs` 已有较多渲染层测试，可继续沿用这一方向。

## 12. 风险与取舍

### 12.1 主要风险

- 自绘 GUI 的视觉调整容易牵一发而动全身
- 顶栏、页面容器、浮层共用几何关系，回归风险较高
- 如果过早补很多新功能按钮，会稀释首轮改造重点

### 12.2 取舍建议

- 首轮只追求“更成熟、更统一”，不追求“功能按钮更多”
- 先把静态布局和状态表达打稳，再补高级状态
- 先对标传统浏览器，再考虑差异化设计

## 13. 结论

ZeroBrowser 当前最缺的不是更多 GUI 功能点，而是成熟浏览器壳应有的：

- 稳定的信息架构
- 克制而统一的视觉层级
- 明确的状态表达
- 更自然的平台整合

因此，GUI 改造应优先围绕顶栏、地址栏、辅助界面统一和页面容器减重展开，而不是先扩功能面。

按本方案推进后，`apps/browser` 应从“能运行的自绘浏览器原型”提升为“具备成熟产品观感的桌面浏览器外壳”。
