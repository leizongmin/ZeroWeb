# M3b wrapKey/unwrapKey AES-KW + jwk 格式（2026-10-17）

crypto.subtle 补齐对称密钥管理面：wrapKey/unwrapKey（AES-KW RFC 3394 +
AES-GCM/CBC/CTR 封装路径）、jwk 导入/导出（AES 家族/HMAC）、spki/pkcs8 对称
NotSupportedError 语义、HMAC/AES 导入 length 成员与 usages 错误次序。
`wrapKey_unwrapKey` 1→**86P/25F**（25F 全为 RSA-OAEP wrapper，M4 域）、
`symmetric_importKey` 84→**606 全绿**、generateKey AES/HMAC 六文件全绿、
serialization aes*/hmac 全绿；意外增益 pbkdf2 **+1,836**、hkdf **+768**
（deriveKey 目标 AES-KW/AES length 成员生效级联）。全量 **+5,069P**
（10,321→15,390，31.5%→46.9%），全绿案 13→27，18 文件增益零回归。

## 改动

1. **host** js_dom_bridge/crypto.rs：新增 `crypto_subtle_aes_kw(mode, key,
   data)`——RFC 3394 wrap/unwrap（IV A6…A6、n≥2 上下限、wrap 输出 A||blocks
   +8 字节、unwrap 校验 A 回 IV 否则空），AES-128/192/256 按密钥字节长分派；
   `crypto_subtle_aes_gcm` 早退守卫放行 16 字节 IV（wrapKey 测试 GCM wrapper
   固定 16B）并补截断路径 (16,16)/(16,24)/(16,32) 三臂。
2. **shim** part02.js：
   - **importKey 重写**：normalize → NotSupportedError；HMAC length===0 →
     DataError（先于 usages 检查，spec 数据复制步骤）；allowedUsages 分
     PBKDF2/HKDF、AES-KW、AES、HMAC 四组；格式分派 raw/jwk/spki/pkcs8——
     对称密钥 spki/pkcs8 → NotSupportedError；jwk 走 kty 'oct'、k base64url、
     use 'enc'/'sig'、key_ops 合法无重复且 ⊇ usages、ext:false+
     extractable:true → DataError、alg 成员须匹配 A{bits}{suffix}/HS{...}；
     HKDF/PBKDF2 extractable:true → SyntaxError；AES 材料字节长 ∈
     {16,24,32}、HMAC 显式 length ∈ (dataBits-8, dataBits]（字节对齐子集，
     非对齐 FIXME）；空 usages → SyntaxError 置于最后（spec 通用步骤 10）。
     keyAlg 输出 AesKeyAlgorithm{length} / HmacKeyAlgorithm{hash 为
     KeyAlgorithm 对象}（WPT helpers.js 取 `key.algorithm.hash.name`）。
   - **exportKey**：raw/jwk；非 extractable → InvalidAccessError；jwk 输出
     `{kty:'oct', k, alg, key_ops, ext}`，alg 映射 A{128,192,256}{CTR,CBC,
     GCM,KW} / HS{1,256,384,512}。
   - **generateKey**：AES-KW usages 限 [wrapKey,unwrapKey]；错误次序非法
     usage SyntaxError → length ∈ {128,192,256} OperationError → 空 usages
     SyntaxError；HMAC length 经 `_zw_keyLengthBits`（显式成员优先，0 →
     OperationError）。
   - **wrapKey/unwrapKey**：wrapper usage/wrap 算法名/目标 extractable 校验 →
     InvalidAccessError；exportKey('raw'|'jwk') 后按 wrapAlgorithm 分派
     AES-KW（`_zw_aesKwCall`）或 AES-GCM/CBC/CTR 直接调块 helper——wrapper
     密钥仅 [wrapKey,unwrapKey] usage，绕开 encrypt() 的 usage 检查（WPT
     wrapKey_unwrapKey 结构）；unwrap 后 jwk 走 JSON.parse + importKey 链。
3. **shim** part01b.js：`_zw_aesGcmCall` IV 接受 16 字节；base64url 编解码
   helper（`_zw_b64uFromBytes`/`_zw_bytesFromB64u`）；`_zw_aesKwCall` 主机
   桥；`_zw_normalizeImportAlgorithm` AES 分支透传 length 成员（deriveKey
   目标 128/192 位生效——pbkdf2/hkdf 增益来源）；HMAC MAC 调用兼容 hash
   对象/字符串两种形态；CryptoKey `Symbol.toStringTag`（WPT
   assert_goodCryptoKey 探针）。
4. **测试**：新增 part53 `test_crypto_subtle_kw_jwk_m3b`——RFC 3394 §4.1
   wrap 向量锚定（KEK 000102…0e0f → wrapped
   1fa68b0a…d2cfe5）、unwrap 回明文、坏输入矩阵（未对齐 payload/篡改密文 →
   OperationError、非 extractable 封装 → InvalidAccessError）、全链 round-trip
   ×3（AES-KW raw、AES-CBC wrapper jwk、256 位 KEK）、错误矩阵 ×7
   （spki 对称 → NotSupportedError、usage 非法/空 usages → SyntaxError）、
   jwk 字段断言 + kty/ext 误用 → DataError、GCM 16B IV 封装 round-trip、
   generateKey 成员断言（AesKeyAlgorithm/HmacKeyAlgorithm/toStringTag）+
   HMAC length 语义 ×2；part05 三处过期断言随新语义修正（jwk HMAC `{}` →
   DataError、exportKey jwk AES 由 NotSupportedError 转 resolves、hash 对象
   形态）。

  M3a 10,321 → **+5,069**，全绿案 13→27，123 文件逐一对比**零回归**

## 剩余

- RSA/EC 签名系（ECDSA、RSASSA-PKCS1-v1_5、RSA-PSS、RSA-OAEP）→ M4；
  wrapKey_unwrapKey 25F 与 rsa/ec_importKey、hmac sign/verify 部分残留均挂此。
- pbkdf2/hkdf 残留 2,052/1,008：badHashName 分类与 0 length 细分语义。
- tentative 域（OCB/ChaCha20-Poly1305/ML-KEM/OKP X25519 系）挂账不修。
- Timeout 1（algorithm-discards-context）与 M3a 持平，非本片范围。
