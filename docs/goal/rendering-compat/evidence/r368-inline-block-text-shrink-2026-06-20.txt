只读探针（LAYOUT_DUMP=1，零代码变更）
================================================================
ifc-011（inline-formatting-context-011.xht）TEST 侧 ZeroWeb 布局树：
  div   h=60  (应 90)
    span h=90 x=8   w=784   <- span1：w=784 = 容器满宽！（应 shrink 到 ~90）
    span h=50 x=8   w=784 y=101  <- span2：w=784，堆叠在第二行（应 y=51 同行）

REF 侧（ZeroWeb 自渲染参考）：
  div   h=90
    img 90×90 x=8 / img 20×50 x=102 / img 50×50 x=122 / img 20×50 x=172（四个 img 同行 y=51）

【关键发现 1】div h=60 是 taffy 主布局块容器高度——确认 R367 结论：taffy 0.7 无 CSS
line-box 概念，inline-block 被映射为 Block（converter convert_display:265），taffy 按
块容器高度计算，与 IFC 行盒解耦。ZeroWeb 的"行盒高度"实际由 IFC（inline_ctx）计算，
非 taffy。

【关键发现 2·新】span w=784（满宽拉伸）是 PRIMARY 缺陷：width:auto 的 inline-block
被 taffy 当 Block 拉伸到可用宽（784），违反 §10.3.9 shrink-to-fit。R180 的
shrink_inline_blocks_to_content 本应收缩，但失败——根因：该函数遍历 LayoutBox 子元素
求宽，而 span 的文本"X"经 measure callback **不产生子盒**（span.children 为空）→
content_max_w=0 → `if content_max_w > 0.0` 守卫跳过 → 不收缩。

【关键发现 3】w=784 连锁：ib_sizes（adjust_inline_block_positions:958）传 span 的
content_width 给 IFC → IFC 见 784 宽 inline-block → 两个 span 无法同行 → span2 堆到
y=101（第二行）→ div h=60 与子元素位置完全解耦。

实验 A（保留）：inline-block 文本内容 shrink-to-fit via intrinsic_sizing
================================================================
修复（float_positioning.rs shrink_inline_blocks_to_content）：把 simplistic 的
laid-out-child-width 循环替换为 intrinsic_sizing::box_content_max_width（已存在，private
→ pub(crate)）。该函数对 inline 级子元素水平求和、block 级递归取最大，且对**无
LayoutBox 子元素的纯文本**按 DOM text_content + 字体度量（estimate_char_width，Ahem
等宽=font_size）累加。span1 "X"@50px Ahem → text_w=50 + frame(border 20×2=40) = 90。

签名加 doc: &Document（engine.rs:241 调用点已有 doc）。

验证（ifc-011 LAYOUT_DUMP after fix）：
  div   h=50
    span h=90 x=8  w=90   <- 收缩到 90 ✓（满宽 784→90）
    span h=50 x=62 w=90 y=51  <- span2 现在同行 y=51 ✓（不再堆到 y=101）
  diff: 11.27% → 1.23%（仍 > 1.0% 阈值 FAIL，但 -10pp）

【span2 x=62 仍重叠】因 ib_sizes 传 content_width=50（非 border-box=90）→ IFC 按 50 宽
排span2 到 x≈62，但 span1 实际 border-box=90（8..98）→ 重叠。见实验 B。

全量 self-source：**442/490 净中性，零翻转**（width-shrink 不翻 PASS 也无回归）。
layout-engine 单测 893/0（+1 新单测 test_inline_block_text_content_shrink_to_fit）。

【裁决】CSS 正确（§10.3.9 inline-block width:auto 应 shrink-to-fit 到 max-content，
含纯文本内容），零回归，改善 P0 簇 ifc-011 度量 10pp。**保留**。是 R366/R367 关闭
IFC 表面修复后重开的「宽度维度」新表面修复（R366=margin / R367=border-box 尺寸 /
R368=width shrink-to-fit 三维度独立）。

实验 B（回退）：ib_sizes content-box → border-box（净 -1）
================================================================
假设：ib_sizes 传 border-box（child.width/height）而非 content-box，IFC 行内贡献含
border/padding，span2 落 x≈102（匹配 REF img2 x=102），消除重叠。R367 单独改此项
net-negative 是因当时 span 仍满宽 784，border-box=784 更糟；R368 width-shrink 后
span=90，border-box=90 才正确。

实验（engine.rs ib_sizes content_width/height → width/height）：
- ifc-011：1.23% → 1.04%，span2 x=62→102（匹配 REF ✓），div h=50 不变。
  仍 > 1.0% FAIL（残余 1.04% = span2 line-height:10px+vertical-align:top 的 glyph
  度量噪声，非布局；div 无背景故 div h=50/90 不影响像素）。
- 全量 self-source：**441/490 净 -1**——multicol-dynamic-change-inside-break-inside-
  avoid-001.html 0.97%(PASS) → 1.05%(FAIL)。该案是 JS 依赖（reftest-wait +
  requestAnimationFrame 未支持→渲染初始态含 .tweak red border 的 <input>），border-box
  改变 input（computed display:inline-block）的 IFC 贡献 ±6px（border 3×2）致越阈值。

【裁决】border-box CSS 更正确（inline-level 行内贡献应含 border）但**净 -1**
（翻一个脆弱 JS 案为 FAIL），按双回归守则**回退**（git checkout engine.rs ib_sizes
回 content_width/content_height）。border-box 维度证伪为单会话不可行（即使 width-shrink
后仍 -1）——multicol/input 交互需更精细守卫或 JS 支持，超单会话。

ifc-011 残余 1.23%（width-only）/ 1.04%（+border-box）均 > 1% FAIL。但残余是 glyph

尝试**，确认为多会话架构（Phase A height-grow reflow）。
