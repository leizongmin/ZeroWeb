────────────────────────────────────────────────────────────────────
1. 决定性排除：footer-img 假设（img 塌缩非 body 压缩主因）
────────────────────────────────────────────────────────────────────
article.html 共 4 张 img：
  line 146  <img width=20 src=data:...>      （正文 h1 前，inline 图标，有 width=20 → 不塌缩）
  line 361  <img src=images/logo_lei.jpg>     （footer「关于作者」区）
  line 376  <img src=images/cc_unavailable.png>（footer CC 许可）
  line 386  <img src=images/qrcode_*.jpg>      （footer 公众号二维码）
⇒ **3 张无 width/height 属性的 img 全在 footer（line 361-386），位于全部正文内容之后**。
R228b 观测的压缩区是 **body y=150-300**（正文），footer 在 y>500。**footer img 塌缩无法解释 body
正文区压缩**（footer img 即便 0 高，只影响 y>500 区域，不影响正文 y=150-525 分布）。
⇒ **排除 R228b 假设①（img 塌缩）作为 body 压缩主因**。即便 img 布局应用有 bug（R233 谱系），
影响域限于 footer，非 67% 主因。主因在正文。

────────────────────────────────────────────────────────────────────
2. 收窄到 body `<pre><code>` 块（12 块，正文主体）
────────────────────────────────────────────────────────────────────
article.html 正文结构（line 151 h1 → line 345 最后 h2）：
  7 个 h2 + 多个 h3 + 22 个 <p> + **12 个 <pre><code>**（line 210-338，正文步骤 1-8 的命令/C 代码）。
代码块 CSS（article.css）：
  .article pre { line-height:1.75; padding:1rem 1.25rem; background:var(--color-code-bg);
                 border-radius:8px; white-space:pre-wrap; overflow-x:scroll; box-shadow:... }
  .article pre code { display:block; min-width:700px; font-size:0.875rem; background:none }

代码块**确为多行**（源码显式 \n）：如步骤4 C 代码 ~12 行、步骤2 install 多行、步骤3 wget/tar 多行。
⇒ chromium 中每 `<pre>` 高 = 行数 × line-height(1.75) × font-size(14px)；12 块多行 code 撑起正文 y=150-600。
ZW 把这些压缩进 y=150-300 = **`<pre>` 块高度严重欠计算**（多行内容未正确累积高度）。

────────────────────────────────────────────────────────────────────
3. 候选机制（待实证探针确认，R164 勿据推断断言）
────────────────────────────────────────────────────────────────────
(a) **`<pre>` IFC 高度欠计算**：pre 内容是 inline 文本经 IFC 渲染。PreWrap preserve_newlines=true
    （engine.rs:1770/text.rs:734 已支持）但**多行高度累积**可能 off——连接 large-font/IFC-storage
    谱系（R84/R101/R125/R210：compute_final_inline_layouts 单行存储守卫、paint IFC 重跑用空 styles）。
    pre 多行内容若只算首行高 → 每块塌到 1 行 → 12 块全压缩到顶部。**最可能**。
(b) **`code{display:block;min-width:700px}` + `pre{overflow-x:scroll}` 交互**：code min-width:700px
    撑宽，pre overflow-x:scroll 应水平裁剪成滚动容器。若 ZeroWeb 未正确施加 overflow-x:scroll 裁剪
    （converter:291 convert_overflow / margin_collapse:35 BFC），700px 宽 code 可能影响 pre 宽度
    或与 pre-wrap 交互异常。**次要**（主要影响水平非垂直，但可能间接）。
(c) **pre-wrap 换行与 chromium 不一致**：长 bash 命令（如步骤2 meson install 多包名）pre-wrap
    换行点不同致行数差异。**次要**（行数差异通常较小，难致 2× 压缩）。

────────────────────────────────────────────────────────────────────
4. 探针配方（实现轮单变量区分）
────────────────────────────────────────────────────────────────────
① LAYOUT_DUMP=1 渲染 morning-work article.html，定位 12 个 `<pre>` 节点，dump 每个 height vs
   预期（行数 × 1.75 × 14px + padding 2rem）。若 height ≪ 预期 → 机制(a) IFC 高度欠计算（主因）。
② 检查 pre 节点 width 是否 = 容器宽（~700-860px）还是被 code min-width 撑到 >860 → 机制(b)
   overflow-x:scroll 裁剪缺失。
③ 对比单 pre 块的 ZeroWeb vs chromium 行数（dump 行盒 vs 截图）→ 机制(c) 换行差异。
每步 product-smoke 区域 diff（沿用 r228 ink-mass/region 方法）量化压缩改善。
