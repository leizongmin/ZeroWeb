# R272 — reftest compare_pixels 比较全 4 通道含 alpha → 输出消费 alpha；补完 R271：clip 白填=parity-correct+死代码，opacity 需 backdrop-capture

**日期**: 2026-06-18
**模式**: 只读源码核实（reftest.rs compare_pixels + R220 ClipPrimitive 生产性 + 输出路径），无代码/reftest 变更
**基线**: 438/490（自源）持平
**承接**: R271（framebuffer 实有 alpha，「无 alpha」前提 false）留开放局限「未追输出/compositing 路径——fb.data 最终是否被合成到不透明白底（若是，clip/transform 清透明 vs 清白等价）」。本轮核实——**结论：reftest compare_pixels 比较全 4 通道含 alpha，输出消费 alpha；R271 的「clip/transform 白填可用 alpha 改」须 refine**。

## 核实

### 1. compare_pixels 比较全 4 通道（含 alpha）

`tests/wpt-runner/src/reftest.rs:1282-1298`：
```rust
for i in (0..fb1.data.len()).step_by(4) {
    let r1=..; g1=..; b1=..; let a1 = fb1.data[i+3];
    let r2=..; g2=..; b2=..; let a2 = fb2.data.get(i+3)...;
    let dr=..; dg=..; db=..; let da = (a1 as i16 - a2 as i16).unsigned_abs() as u8;
    let channel_max = dr.max(dg).max(db).max(da);   // ← alpha 差计入 max
    if channel_max > threshold { diff_pixels += 1; }
}
```
→ **alpha 通道参与对比**（da 计入 channel_max）。reftest **不 strip alpha、不强制合成到不透明**——直接 RGBA 逐通道比。reftest.rs:674 注释印证（「alpha=0 退化透明…假通过根因」）——alpha 比较专为**抓透明退化 bug**而设。

### 2. 故 reference 不透明 → ZeroWeb 须渲染 alpha=255

reference（chromium 截图 / ZeroWeb 自渲染 ref）均为**不透明**（页面截图 alpha=255）。故 ZeroWeb framebuffer 每像素须 **alpha=255** 才 parity。framebuffer `new()` 初始化透明 [0,0,0,0]（surface.rs:52）→ **未绘制区会 alpha=0 diff**；clip 清白 [255,255,255,255]（alpha=255）**匹配不透明 ref = parity-correct**，清透明 [0,0,0,0] 反会 alpha-diff。→ **clip 白填对 reftest parity 是正确的（非 bug）**。

### 3. clip 白填更是死代码（R220）

R220 已立：engine 生产路径**从不生成 ClipPrimitive**（`add_clip` 0 处非测试调用），overflow 裁剪在 paint 阶段由 `clip_all_primitives_to_rect` 预烘焙进图元几何。故 cpu/mod.rs:163 的 clip loop + apply_clip（白填）**生产中 primitives.clips 恒空 → 不执行**。→ R270 的「clip 近似」定性针对**死代码**，非真实 manifesting 近似。真实 overflow 裁剪 = 几何预烘焙（不同机制，非白填）。

## 对 R271 的 refine（修正「clip/transform 白填可改」乐观）

R271 称「framebuffer 有 alpha，clip/transform 白填=白底假设可改」。R272 refine：
- **clip 白填**：① reftest parity-correct（对比用 alpha，不透明 ref 须 alpha=255，白填对，清透明反 diff）；② 死代码（无 ClipPrimitive 生产）。→ **非「可改」的 bug，是 parity-correct 的死代码**。
- **transform 白填**（apply_transform_post 暴露区填白）：仍可议（transform 暴露区填白假设白底，嵌套/非白背景场景错），但 transform 本身是近似（R269），且 opacity/transform reftest 用例 footprint ≈0（R250）。
- **opacity RGB-darken**：在 **RGB 通道**与 chromium 真合成（elem*amt+bg*(1-amt)）diff——非 alpha 问题。post-process 无法 backdrop-capture（元素已覆盖背景）→ 须绘制期 alpha（架构）。**有 alpha 也不解**（约束是 post-process 架构 + 不透明 ref，非格式）。

## 净结论

- **framebuffer 有 alpha（R271）+ reftest 比较用 alpha（R272）**——但 reference 不透明 → ZeroWeb 须输出 alpha=255。故「alpha 可用」**不解 opacity/clip post-process 近似的 reftest parity**（opacity 需 backdrop-capture/绘制期 alpha；clip 白填已 parity-correct+死代码）。
- **alpha 可用真正惠及 glyph/image/shadow 合成**（已用 blend_pixel，R271）——这些是「绘制期」合成（源 alpha 已知、背景在 fb），非 post-process。
- **R271 caveat「clip/transform 白填可改」须收窄**为「clip 白填=parity-correct 死代码（R220 无生产 ClipPrimitive）；transform 白填可议但低 footprint；opacity 需 backdrop-capture（post-process 架构约束，非格式）」。

## 对优先级队列的影响

不改变 DC-9 是 active forward motion。细化 DC-8/DC-9 近似性质：opacity/clip/transform 的 post-process 近似**非简单「启用 alpha」可修**——opacity 须架构（绘制期 alpha/backdrop-capture），clip 是死代码+parity-correct（real overflow-clip 走几何预烘焙）。blend（R269 stub）仍是 DC-8/DC-9 最实质共同缺口。framebuffer-alpha 真实价值在 glyph/image/shadow 已用，非在修 post-process 近似。

## 局限（诚实）

- 未独立确认所有 reference PNG 均 alpha=255（页面截图惯例如此，且 reftest.rs:674 注释示 alpha 比较抓退化，反证 ref 预期不透明）；若有透明 reference（罕见），结论须复核。
- 未追 browser 窗口 present 路径是否合成到不透明（GPU surface present，可能平台合成；非 reftest 范畴，reftest 是 fb 对比）。
