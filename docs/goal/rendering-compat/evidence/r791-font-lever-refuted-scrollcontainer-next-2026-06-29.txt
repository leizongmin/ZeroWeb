1. R790 推荐 lever（NORMAL_LINE_HEIGHT_RATIO → 真实字体度量）REFUTED
================================================================================

R790 推荐：把 inline/text_metrics.rs 的 NORMAL_LINE_HEIGHT_RATIO（1.2，用于 line-height:normal）
改为 fontdue 真实度量（DejaVuSans=1.1641），称此为 welcome 16% 根因。

A/B 实验（1 行 const 改动 + product-smoke）：
  - baseline:        welcome 16.16%（77588/480000 px）
  - ratio 1.2→1.1641: welcome 16.60%（79681/480000 px）  ← +0.44pp 更差
  → 回退（字节同 HEAD）

REFUTED 根因（cheap check 即证伪）：
  welcome.html 全部用**显式 line-height**（Number 值），从不用 normal：
    line 12  font-family: sans-serif       (body, 无 line-height → normal 继承)
    line 68  line-height: 1.08
    line 77  line-height: 1.5
    line 124 line-height: 1.45
    line 164 line-height: 1.25
  NORMAL_LINE_HEIGHT_RATIO 仅对 LineHeightValue::Normal 生效（text_metrics.rs:194-204）。
  welcome 主要可见文本（hero/cards/正文）全用显式 Number line-height → ratio 改动**零影响**。
  仅 body 默认等少数 normal 继承元素受影响，且 1.1641 < chromium 实际 → 反而 +0.44pp 发散。

裁决：R790「welcome 16% = NORMAL_LINE_HEIGHT_RATIO font-wall」**误诊**。welcome 16% 真因是
行盒**基线/ascent 定位**（apply_vertical_alignment mod.rs:1776 baseline_y=max_ascent，文本运行
ascent≈font_size 近似），需 fontdue 真实 ascent/descent 接入 layout——即 R633 确认的 Phase-A
多会话死锁区（layout-engine 无法访问真实字体度量，仅见 CSS font_family 字符串，见 §3）。
R790 PIL 的「行高多 ~3px」来自显式 line-height 计算后的基线定位，非 normal-ratio。

★ 教训（再证 R740）：doc-side 只读归因假阳性率高。R790 PIL 分析未先核查 welcome 实际用
normal 还是显式 line-height。cheap empirical check（grep CSS + 1 行 const A/B）即推翻。
勿再以「NORMAL_LINE_HEIGHT_RATIO font-wall」为 welcome diff 归因。

3. layout-engine 字体度量架构事实（确认 Phase-A 死锁边界，R633 再证）
================================================================================

Explore agent 确证：
  - DEFAULT 字体 = DejaVuSans（Linux，apps/renderer/src/main.rs load_system_fonts）
  - resolve_font_metrics（text_metrics.rs:178）签名 (Option<&ComputedStyle>) → (font_size, line_height)
    仅见 CSS font_family **字符串**，**无 font_id / 无真实字体度量访问**
  - layout-engine 用启发式：estimate_char_width（0.55×ASCII 等）+ strut_ascent（line_height×0.8，
    mod.rs:1756）+ ascent≈font_size（mod.rs:1766/213）
  - font_id 解析在 **paint 层**（Painter::resolve_font_id，mod.rs:249），layout 层不可见
  → 「行盒基线用真实 ascent」须 IFC↔FontLoader plumbing（font-family→font_id 预解析 +
    水平/垂直度量传入 layout）= R223/R188 Phase-A 核心，多会话架构，高风险

结论：morning/welcome ~17% diff 的真根因（行盒基线度量）是 Phase-A 多会话死锁区。
R630/R632/R759 已落地所有**不依赖字体度量**的行盒修复（多行 y 分行 / line-height CSS 响应 /
Ahem normal-ratio 1.0）。残余全依赖 Phase-A plumbing。
