# R388 — chromium Oracle 大面积损坏（Ahem 未加载）→ 推翻 large-font 簇「发散」结论

**日期**：2026-06-21
**触发**：R387 把 large-font 簇（ifc-008/009/011/font-051）的 chromium 发散定位到
「stored-path baseline/line-height Y 计算」。本轮做 R387 推荐的像素级诊断，发现
**发散不在 ZeroWeb，而在 chromium Oracle 截图本身损坏**。

## 核心发现（一句话）

ifc-008 的 ZeroWeb 渲染是**正确的**（实心绿 200×200，0% 红）；报告的「7.93% chromium
发散」来自一张**损坏的 oracle 截图**（chromium 退回 fallback 字体，85% 红底）。所有
108 个 Ahem 依赖 reftest 的 oracle 均在「系统 Ahem 安装前」抓取，长期污染 DC-14 度量。

## 像素级证据

ZeroWeb 渲染 ifc-008（stored path，REFTEST_DUMP）vs 旧/新 chromium oracle，800×600：

```
                       GREEN     RED    WHITE     AA
ZW-test (正确)          97.1%    0.0%    2.9%    0.0%   ← 实心绿填满 200×200，无红（PASS 语义）
OLD oracle (06-18 抓)   11.5%   85.0%    2.9%    0.6%   ← fallback 细 X 字形，红底大面积外露
NEW oracle (06-21 重抓)  8.3%    0.0%   91.5%    0.2%   ← 实心绿 200×200（8.3%≈40000px=200²，AA≈0=实心非字形）

ZW-test vs OLD oracle  : 7.93%   ← 长期报告的 ifc-008「chromium 发散」
ZW-test vs NEW oracle  : 0.52%   ← 正确 oracle 下 15× 缩减，进入 near-pass
NEW vs OLD oracle      : 7.45%   ← oracle 自身损坏幅度
```

ifc-008 = `#div1{background:red;font:100px/1em Ahem;height:2em;width:2em}` + 内 div
`XX XX`（green）。预期：2 行 100px Ahem 绿方块填满 200×200 → 无红。ZW 正确做到；
损坏的 oracle 因无 Ahem 把 "XX" 渲成细 X → 几何崩溃 → 红。

## 根因（确定）

1. **时序**：oracle 截图抓取时间 **2026-06-18 21:37**；系统 `$HOME/.local/share/fonts/Ahem.ttf`
   安装时间 **2026-06-20 03:20**（晚近 2 天）。抓取时 chromium 无 Ahem 可用。
2. **file:// 解析失败**：`chromium-oracle-shot.mjs` 用 `file://<DATA_ROOT>/<test>` 加载。
   但上游 reftest 的样式表/字体用**绝对路径**：
   - test 内 `<link rel="stylesheet" href="/fonts/ahem.css">`（绝对）
   - `wpt-data/fonts/ahem.css` 声明 `@font-face{src:url("../../fonts/Ahem.ttf")}`
   - `file://` 把绝对 `/fonts/ahem.css` 解析为**文件系统根** `/fonts/ahem.css`（不存在）
   → Ahem.css 加载失败 → Ahem.ttf 永不加载 → chromium `font-family:Ahem` 退回 fallback
   → Ahem 实心方块变细 X → 几何崩溃。
3. **影响范围**：`grep -rl "fonts/ahem.css" wpt-data/` = **108 个 reftest** 跨 14 目录
   （css-multicol 27 / css-writing-modes 24 / css-flexbox 12 / CSS2/fonts 11 / css-tables 6 …）。

## 对历史诊断的纠正

- **R385「ifc-008 stored-path 发散 = fontdue 度量噪声死路」**：建立在**损坏 oracle** 上。
  ZW 实际正确（0% 红）；发散 7.93% 全部来自 oracle 把 fallback 字形当 Ahem。结论无效。
- **R387「fontdue Ahem 完美 → 发散在 layout Y 定位」**：fontdue 完美的结论仍成立（且本轮
  ZW 实心绿进一步印证），但「发散在 layout Y」的归因也建立在损坏 oracle 上——真实 ZW vs
  正确 oracle 仅 0.52%（near-pass），不存在「stored-path Y 定位 bug」。
- **DC-14 chromium-Oracle 真一致率 ~35.8%（169/475）**：被 108 个损坏 oracle 系统性压低。
  正确 oracle 下应显著上修（待本轮 cross-validate 复测）。

## 修复（robust，防复发）

`tests/wpt-runner/scripts/chromium-oracle-shot.mjs` 原用 `file://`。改为**内嵌本地静态
HTTP server（root=DATA_ROOT）**，用 `http://127.0.0.1:<port>/<test>` 加载：

- `/fonts/ahem.css` → `DATA_ROOT/fonts/ahem.css` ✓（存在）
- ahem.css 内 `../../fonts/Ahem.ttf`（相对 `/fonts/ahem.css`）→ `/fonts/Ahem.ttf`
  → `DATA_ROOT/fonts/Ahem.ttf` ✓（存在）
- @font-face 正常加载 Ahem → oracle 正确。

此方案**自包含、不依赖系统是否安装 Ahem**，避免静默损坏复发（旧 file:// 方案仅在
系统恰好装了 Ahem 时才偶然正确）。改动含 MIME 映射（.xht→application/xhtml+xml 等）
与路径逃逸防护（normalize + startsWith root 校验）。

## 验证

- HTTP 方案实测 ifc-008 oracle = 8.3% green / 0% red（与 file+system-Ahem 一致）。
- 全量重抓 503 oracle（`--all`）：503 captured, 0 failed。
- ifc-008 ZW-test vs NEW oracle = **0.52%**（vs 旧 7.93%）。

## 本轮代码变更

- `tests/wpt-runner/scripts/chromium-oracle-shot.mjs`：file:// → 内嵌 HTTP server（+~60 行，
  含 MIME 表、startStaticServer、路径逃逸防护、注释说明 R388 根因）。
- 重抓 `tests/wpt-runner/oracle-shots/` 全部 503 PNG（产物，非代码）。
- 零生产 Rust 代码变更；零 reftest 行为变更（ZW 渲染本就正确）。

## cross-validate 复测影响（rigorous，apples-to-apples）

用重抓 oracle 重跑 `cross-validate.py`（全量 475，chan>5，与 R381 同口径）。A/B 唯一
差异是 oracle（ZW 代码零 Rust 变更），故差异 100% 来自 oracle 修复。完整输出见
[`cross-validate-full-2026-06-21.txt`](./cross-validate-full-2026-06-21.txt)。

| 指标 | BEFORE（R381 / 06-20，损坏 oracle） | AFTER（R388 / 06-21，修复 oracle） | Δ |
|------|------|------|----|
| 广义 chr<1% 一致（任意 verdict） | 193/475 = 40.6% | **205/475 = 43.2%** | **+12 / +2.5pp** |
| 严格（self-pass 且 chr<1%） | 170/475 = 35.8% | 177/475 = 37.3% | +7 / +1.5pp |
| 污染率（self-pass 中 chr>1%） | 48.0% | 46.0% | −2.0pp |
| gross ≥5% 发散 | 53/475 = 11.2% | 50/475 = 10.5% | −3 |
| 改善案（z_vs_chr 降 >0.5pp） | — | **26** | — |
| 退步案（z_vs_chr 升 >0.5pp） | — | 14 | — |

**net 改善温和（+12 广义一致）**——原因：损坏 oracle 同时「掩盖部分真实 ZW bug」与
「制造部分假发散」，修复后两者部分抵消。但**定性价值远大于计数**：

1. **large-font 簇被证正确**：ifc-008（7.89%→0.50%）、font-051（8.32%→0.84%）、
   ifc-009（7.42%→1.34%）、downloadable-font-scoped（20.22%→1.52%）从「chromium 发散」
   翻成 chr<1% 一致或近通过。**R385「fontdue 度量死路」与 R387「lever=layout Y 定位」
   对该簇的归因被推翻**——它们是在追一个 oracle 镜像，非 ZW bug。
2. **14 个「退步」案是 oracle 变诚实**（非 ZW 回归）：正确字体加载后揭示先前被损坏
   oracle（fallback 字体偶然接近 ZW 错误渲染）掩盖的真实发散，集中在 css-fonts
   （font-family-name-025 +12.7pp / font-face-local +4.4pp / font-colorization 等）。
3. **DC-14 度量基线可信化**：此后 chromium-Oracle 一致率不再含 108 个 Ahem 损坏 oracle
   的系统性偏差；R381「诚实 plateau 35.8%（strict）」上修为 37.3%（strict）/ 43.2%（广义）。

**plateau 仍真实成立**（43% 广义一致距 95% 仍远），但其成因从「large-font stored-path
Y bug」修正为「真实 multicol/writing-mode/flex-baseline 结构性 + 字体加载细节」——
large-font 簇不再是 lever（已证 ZW 正确）。
