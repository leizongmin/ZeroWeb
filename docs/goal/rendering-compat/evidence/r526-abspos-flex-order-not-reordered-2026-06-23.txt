测试（flexbox-paint-ordering-003.html）
--------------------------------------
- `.container { display:flex }` 含两个 abspos 子元素：
    .absPosHighOrder { position:absolute; order:10; } 含 .redBlock（100×100 红）  ← DOM 第 1
    .absPosLowOrder  { position:absolute; order:5;  } 含 .limeBlock（100×100 lime）← DOM 第 2
- 期望（ref = limeSquare）：abspos 不是 flex item → `order` 无效 → 按 DOM 顺序绘制 →
  red 先绘、lime 后绘 → lime 在上 → 显示 lime。
- ZeroWeb 旧行为：按 order 重排 → order:5 的 lime 先绘、order:10 的 red 后绘 →
  red 在上 → 显示红 → 2.08% diff（10000px = 100×100 红 block 露出）。

机制定位
--------
CSS Flexbox §8.1：`order` 只重排 in-flow flex item；abspos（position:absolute/fixed）
不是 flex item，其绘制顺序遵循 CSS Appendix E step 6（positioned descendants 按 tree
order 绘制），不受 `order` 影响。

两处排序点：
1. tree.rs:489 `children_with_order.sort_by_key(|(_, order)| *order)` — 建布局树时收集
   **所有**子元素（含 abspos）按 order 排序。主导点（决定 LayoutBox 树结构）。
2. engine.rs:1156 `sort_children_by_css_order` — 后处理 LayoutBox 树，对 flex/grid 容器
   子元素再次按 css_order 稳定排序（key = (order, idx)）。

上轮只改 site 2 → 被 site 1 抵消（site 1 建树时已重排）→ 无效。正确修复 = 两站点一致。

修复（~10 行，两站点）
----------------------
两站点对 abspos 子元素用 0 作 order 排序键（而非其真实 order 值）。stable sort 保持
abspos 的 DOM 相对顺序；in-flow 子元素仍按真实 order 重排。

- tree.rs:484-496（Element 分支读 order）：
    let order = styles.get(&child_dom).map_or(0, |s| {
        if matches!(s.position, PositionValue::Absolute | PositionValue::Fixed) {
            0  // abspos 不受 order 重排，stable sort 保持 DOM 顺序
        } else {
            s.order
        }
    });
- engine.rs:1182-1199（has_non_zero_order 守卫 + sort key）：
    守卫：`!c.is_absolute && c.css_order != 0`（abspos 不触发排序）
    sort key：`.map(|(i, c)| (i, if c.is_absolute { 0 } else { c.css_order }))`

为何 order=0 安全：abspos 经 R504 全局 positioned-descendant 延迟在 paint step 6 按
tree order 单独绘制，故其 in-vec 相对位置只影响 (a) in-flow 布局顺序（abspos 出流，
不占 main-axis）—— 无影响；(b) abspos 自身 tree-order 绘制顺序 —— 正是要保持 DOM 顺序
的目标。in-flow/abspos 混合时 abspos 经 stable sort 落在 order-0 组内按 DOM 排列，绘制仍
由 painter step 6 统一延迟处理（与 in-flow 隔离），语义不变。
