# R271 — framebuffer 实有 alpha：「alpha 总为 255 / 无 alpha」前提 FACTUALLY FALSE（effects.rs:138/apply_clip/apply_transform_post）；opacity 近似真因=post-process 架构，clip/transform 白填=白底假设

**日期**: 2026-06-18

**基线**: 438/490（自源）持平
**承接**: R268（opacity 经 RGB 变暗近似）+ R269（transform 白填）+ R270（clip 清白、3 近似根因「framebuffer 无 alpha」）均把「framebuffer 无 alpha / alpha 总为 255」当作既定约束。本轮核实该前提——**证伪**：framebuffer **实有 alpha**，「无 alpha」是**错误前提**（code comment 与多处实现不符）。

## 证伪（全源码闭合）

### 1. FrameBuffer 是 RGBA（4 字节/像素，alpha 通道存在）

`crates/render-foundation/src/surface.rs:40-104`：
```rust
pub struct FrameBuffer {
    pub data: Vec<u8>,   // 像素数据（RGBA，行优先）
    pub width: u32, pub height: u32,
}
impl FrameBuffer {
    pub fn new(w, h) -> Self { let data = vec![0u8; (w*h*4) as usize]; ... }  // 初始化 [0,0,0,0] 透明！
    pub fn get_pixel(&self, x, y) -> [u8; 4] { ... 返回 4 字节含 alpha }
    pub fn set_pixel(&mut self, x, y, rgba: [u8; 4]) { ... 存全 4 字节含 alpha（不强制 255） }
    pub fn clear(&mut self, r, g, b, a) { ... 接受 alpha 参数 }
}
```
→ **格式 RGBA，alpha 通道存在；set_pixel 忠实存 alpha；new() 初始化为透明 [0,0,0,0]（非不透明）**。

### 2. blend_pixel 存在且被真 alpha 合成消费

`cpu/mod.rs:584 fn blend_pixel(fb, x, y, color, alpha)` —— alpha 合成 helper。**调用点**：glyphs（:456 真字形 alpha）、images（:625/:678 真图 alpha）、shadow（shadow.rs:96 get_pixel+blend）、fills/rounded（:332/:376 传 alpha=255 即不透明覆写）、gradient（gradient.rs:155 blend）。
→ **alpha 合成在 ZeroWeb CPU 是一等公民**（glyph/image/shadow 都用真 alpha）。reftest 路径 `main.rs:305 fb.data = rgba`（png EXPAND）—— reference PNG 以 RGBA 加载对比。

### 3. 「alpha 总为 255 / 无 alpha」前提 FALSE

- effects.rs:138 注释「帧缓冲 alpha 总为 255」justify opacity 用 RGB 变暗——**与 surface.rs 事实矛盾**（alpha 忠实存储，glyph/image/shadow 用真 alpha）。
- apply_clip（:685-714）清裁剪区外为 [255,255,255,255]（白不透明）——comment 隐含「无 alpha 须白填」，**false**（可清 [0,0,0,0] 透明）。
- apply_transform_post（:720-786）暴露区填白——同 false。

→ 「framebuffer 无 alpha」**不是格式约束，是 code 选择 / 错误前提**。

## 近似的真实根因（非「无 alpha」）

### opacity（RGB 变暗）真根因 = POST-PROCESS 架构，非格式

FilterPrimitive::Opacity 作**后处理**（元素已绘制在背景之上后再乘 RGB）。真 opacity 合成 = `element*amount + backdrop*(1-amount)`，但后处理时**背景已被元素覆盖、丢失**，无法恢复 → 只能 RGB 变暗近似。**即便 framebuffer 有 alpha，后处理也无法做真合成**（除非先捕背景层 = blend-mode 的 source+dest 问题）。
→ **真修 opacity 须在元素绘制期间应用 alpha（每个 fill/glyph blend 时 alpha*=amount），非后处理**——架构改动，非「启用 alpha」即可。

### clip / transform 白填真根因 = 白底假设，可用 alpha 改

apply_clip 清外为白、apply_transform_post 暴露区填白——**假设背景是白**。对顶层页面（白背景）偶然对；对**嵌套元素/透明 surface**（SurfaceDescriptor 有 `with_transparency()`，透明是一等概念）是 bug（应清透明让真背景透出）。**有 alpha 支持，clip/transform 可清 [0,0,0,0] 透明替代白填**——可改（非格式阻塞）。

## 对 DC-8/DC-9 的影响

- **R268/R270 caveat「framebuffer 无 alpha」纠正**：framebuffer 实有 alpha。R268「DC-9 opacity sound」仍成立（GPU 正确复刻 CPU 当前 RGB-变暗行为 = DC-9 parity 想要的），但 R268 caveat 的「无 alpha」理由**错误**——opacity 近似真因是 post-process 架构。
- **DC-8 三近似非格式阻塞**：opacity 须架构改（绘制期 alpha）；clip/transform 可直接改清透明（小改，但须核输出路径是否真用 alpha——见下局限）。
- **blend（R269 stub）与 alpha 正交**：blend 需 source+dest 双图层（与 opacity-post-process 同源「背景丢失」问题），非「无 alpha」。

## 局限（诚实）

- 未完整追输出/compositing 路径：fb.data 最终是否被合成到不透明白底（若是，clip/transform 清透明 vs 清白在最终像素**等价**，则白填非 bug）。reftest reference 多为不透明（chromium 在不透明上渲染），故 reftest 视角白填与透明-合成-到-白 等价；但**透明 surface / 嵌套场景**白填是 bug。本轮证实「格式有 alpha + 近似是 code 选择」，未量化输出路径对 alpha 的最终消费——留后续。
