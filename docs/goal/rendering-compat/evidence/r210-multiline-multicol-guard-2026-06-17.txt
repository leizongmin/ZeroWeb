# R210：compute_final 多行存储 + multicol 守卫实证（docs-only，基线 439/490）

## 假设
R209 记录 PHASEA_MULTILINE（允许纯 Ahem 多行存储）净负——改善 ifc-008/009 但回归
multicol-fill-auto-001（R198 反向依赖）。本轮在 compute_final_inline_layouts 的多行
存储条件上加 `!in_multicol` 守卫（in_multicol 经 R210 新增的递归参数从 multicol 容器
透传到后代），假设可在修 ifc-008/009（非 multicol）的同时保护 multicol-fill-auto。

## 守卫实现
- compute_final_inline_layouts 增加 `in_multicol: bool` 参数，
  `child_in_multicol = in_multicol || root.is_multicol` 递归透传。
- `allow_multiline = PHASEA_MULTILINE==1 && is_pure_ahem && !in_multicol`
- text.rs:830 stored frag 渲染改 `y: f.y + line.y`（frag.y 行内相对→绝对，多行必需）

## 全量实测（make reftest-upstream 等价，490 用例）
- default（无 gate）：439 PASS / 51 FAIL
- gate（PHASEA_MULTILINE=1 + !in_multicol 守卫）：439 PASS / 51 FAIL —— **净 +0**
- 仅 2 个用例翻转：
  - ✅ ifc-008: 8.18% FAIL → PASS 0.00%（compute_final 正确存储 node39 的 2 行 100px Ahem）
  - ❌ multicol-fill-auto-001: 0.63% PASS → 9.15% FAIL

## 根因精确定位（multicol-fill-auto 回归源 = ref 的 float div，非 multicol 容器）
CFDEBUG 探针（reftest 双趟，正确加载 /fonts/ahem.css）显示 multicol-fill-auto 存储了
node 25（10 行 16 frag）/ node 28（5 行 8 frag），**in_multicol=false**。

逐文件分析：
- test 文件：1 个 multicol div（column-count:3 column-fill:auto > 直接文本）
- **ref 文件**：2 个 `<div float:left width:10em>`（**非 multicol**，用 float 模拟列），
  各含 5–10 行纯 Ahem 文本

→ node 25/28 是 **ref 文件的 float div**，合法地 in_multicol=false，`!in_multicol` 守卫
**无法区分**它们（它们本就不是 multicol 内容）。回归不在 multicol 容器，而在 ref float div。

## 为什么 ref float div stored 会回归（v_offset 语义墙）
- default（多行守卫挡住）：ref float div 走 paint IFC（text.rs:1220 else 分支），
  用 `baseline_fs = font_size` 做 baseline offset。
- gate（多行存储）：ref float div 走 stored 路径（text.rs:1202），用 `v_offset = 0`（Ahem
  位图顶部对齐行盒顶部）。
- 两条路径对同一多行 Ahem 文本的 baseline 计算不同（stored=0 vs paint IFC=font_size），
  ref（stored）与 test（paint IFC column 分配）渲染不一致 → 9.15%。

## 实测 v_offset=font_size（统一两条路径）—— 破坏单行用例
把 stored 路径 v_offset 从 `if is_ahem {0} else {font_size}` 改为 `font_size`：
- multicol-fill-auto-001: 9.15% → 10.30%（更差）
- font-051: PASS → 16.67% FAIL（单行 large-font 被破坏）
- ifc-008: 0.00% → 8.33%（重新失败）

→ stored 路径 v_offset 单行/多行语义无法统一，印证 R125 三路径死锁。

## 关键纠正既往记录
1. **R209「R198 ancestry-guard 墙」机制精化**：ancestry 守卫失效不是因为「multicol 子内容
   非 ancestry-tracked」，而是 multicol-fill-auto 的回归源是 **ref 文件的 float div**（合法
   非 multicol），任何 multicol-ancestor 守卫都无法触及它。
2. **product-smoke 单趟诊断陷阱**：product-smoke 不加载外链 CSS（base_dir=None），
   multicol-fill-auto 的 /fonts/ahem.css 不解析 → is_pure_ahem=false → 不存储。
   故 R209 用 product-smoke 看不到 multicol-fill-auto 的存储行为（误判其不受影响）。
   **涉及外链 CSS 的用例必须用 reftest 双趟路径诊断，product-smoke 仅对内联 CSS 用例可靠**。

## 结论
compute_final 多行存储 + multicol 守卫 **净 +0，不可默认启用**（zero count 回归标准）。
真正的阻塞 = **stored 多行路径与 paint IFC 路径的 v_offset/baseline 语义在多行场景不一致**，
通过 ref float div 暴露。这是 Phase A IFC 双路径统一问题（R125/R198 同墙），单点不可解。
ifc-008 已确认可被 compute_final 正确存储并 PASS，但解锁它需要先统一 stored 与 paint IFC
的多行 baseline 语义（结构性多轮），或找到一个能让 ref float div 多行 stored 与 paint IFC
像素一致的 v_offset 公式（本轮 font_size/0 两极均失败）。

无代码变更（实验已 git checkout 回 R207 e0e2689 干净态），基线 439/490 持平。
