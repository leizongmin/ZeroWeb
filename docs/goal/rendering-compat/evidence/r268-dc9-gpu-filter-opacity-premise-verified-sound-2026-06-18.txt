## 核实结论：前提 SOUND（区别于 R236/R238 的 flawed premise）

### 1. 语义对齐：GPU fs_opacity == CPU apply_filter Opacity

**CPU 参考**（cpu/effects.rs:133-151）`FilterKind::Opacity(amount)`：
```rust
for y in top..bottom { for x in left..right {   // filter.rect 区域
    let p = fb.get_pixel(x, y);
    fb.set_pixel(x, y, [(p[0] as f32 * amt).round().clamp(0,255), ..., 255]);  // RGB*=amt, alpha=255
}}
```
区域 = filter.rect 缩放后钳到 framebuffer 界（effects.rs:24-27）。

**GPU shader**（pipeline.rs:422-426）`fs_opacity`：
```wgsl
let c = textureSample(src_texture, src_sampler, in.uv);
let a = max(0.0, min(1.0, uniforms.amount));   // amount 钳 [0,1]
return vec4f(c.r * a, c.g * a, c.b * a, 1.0);   // RGB*=a, alpha=1.0
```
区域由 render pass scissor rect 限定（pipeline.rs:381-382 注释）。

→ **语义一致**：区域 RGB *= amount，alpha 强制不透明（framebuffer 无 alpha 通道）。GPU 显式钳 amount 到 [0,1]（CSS opacity 本就 [0,1]，GPU 更严谨），CPU 仅钳结果——对合法 opacity 输入两者一致。

### 2. ping-pong 正确（R249 缺的第二纹理已落地）

renderer/mod.rs:99 `headless_texture_b: Option<wgpu::Texture>`（注释「无头 ping-pong 第二纹理（DC-9 后处理）」）——**R249 标的「缺第二张纹理」现已就位**。

`apply_opacity_filters_headless`（renderer/mod.rs:791-834+）ping-pong 流程（注释 788-790）：
1. copy A→B（B 获完整场景基底）
2. scissor pass 采样 A 写 B（filter.rect 内 RGB *= amount）
3. copy B→A（结果回 A 供 read_pixels）
多 filter 逐个 ping-pong，最终结果在 headless_texture(A)。

→ **正确规避 wgpu「同 pass 不能读写同一纹理」约束**（R249 前提），且 scissor 钳到 [0,width]×[0,height]（:834）匹配 CPU 的区域钳制。

### 3. headless-only，零默认回归

- 仅 headless 路径（reftest `--gpu`/测试）实现；窗口 surface 路径不变（spec 明确）。
- 无 filter 时不触发（`opacity_filters.is_empty()` 守卫，:779）→ 438 CPU reftest 完全不受影响；GPU 无 filter 的 case 不变。
- 仅 `FilterKind::Opacity` 起步（DC-9 三缺口 transform/filter/blend 之一）；blur/transform/blend 后续同模式扩展。

## 与 R236/R238 的对比（为何这条 sound 而那两条 flawed）

- R236（R260 spec）：前提「multicol.rs 填 taffy_baseline → 被 engine.rs:988 消费」**flawed**——消费者 guard 仅 InlineFlex|InlineGrid 不覆盖 baseline-export 的 block flex（R266 证伪，field-fill 净 0）。
- R238（R262 spec）：前提「engine.rs:1407 需加 vertical-rl mirror」**flawed**——IFC vertical_rtl 分支已镜像 fragment.x，mirror 会双重镜像（R267 证伪）。
- **DC-9 opacity（1d50409 spec + 实现）**：前提「GPU 区域 RGB*=amount == CPU Opacity」**sound**——CPU 参考语义清晰（effects.rs:133-151 直接可读），GPU fs_opacity + scissor + ping-pong 逐点对齐，无「未核 guard / 未核上游已做变换」类盲点。

**差异根因**：R236/R238 的 spec 基于读 engine.rs 行号 + 残余差推断「缺某步骤」，未核消费者 guard / 上游 IFC 是否已做该变换；DC-9 opacity 的 spec 基于读 CPU 参考实现（effects.rs 直接给语义）+ 照搬，前提锚定在明确的 CPU 语义而非推断。

## caveat（不改变 DC-9 覆盖结论，但须知晓）

**CPU+GPU 均以 RGB 变暗近似 opacity**（framebuffer 无 alpha 通道，不能做真 alpha 合成）。故：
- **DC-9 覆盖满足**：GPU 能渲染 FilterPrimitive::Opacity 图元且与 CPU 一致（覆盖 + 双模式对齐，DC-9/DC-10 对 opacity 项达标）。
- **但 filter:opacity reftest 仍可能 diff chromium**：chromium 做真 alpha 合成（元素与背景混合），ZeroWeb CPU+GPU 均只变暗元素像素（不与背景混合）。这是 **CPU 既有近似**（非 GPU 引入），R250 已立 DC-9 为低 reftest 杠杆（footprint ≈0）。opacity 近似正确性是更深的独立问题（framebuffer alpha 通道架构），非 DC-9 覆盖门禁、非本轮范围。
