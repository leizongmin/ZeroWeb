#1  flex-abspos-inset-nested-001 (8.33%) / -002 (18.75%)  → 复杂（2 个互相依赖 bug）
----------------------------------------------------------------
结构：.outer-flex(height:200) > .flex-item(width:100%) > .intermediate(position:relative,height:100%)
      > .inner-flex(display:flex, position:absolute, top:0, bottom:0) > img(1x1-green, display:block)
期望（chromium）：200x200 绿块（001）/ 300x300（002）—— img 高度被 flex align-items:stretch
      拉到容器高（200/300），宽度经替换元素固有宽高比（1:1）从确定高度导出 = 同值。
ZeroWeb 实测（LAYOUT_DUMP）：
      div.inner-flex  abs_y=51 h=200  w=0.0   ← width=0
        img           abs_y=51 h=200  w=0.0   ← 继承父 0 宽
      fills=0 images=0 → 完全不渲染绿（diff = 整块绿区 40000/90000 px）
根因 = 2 个互相依赖 bug：
  (A) abspos §10.3.7 shrink-to-fit 缺失：.inner-flex 是 abspos 且 left/right/width 全 auto，
      应 shrink-to-fit 到内容（CSS 2.1 §10.3.7），但 ZeroWeb 无 abspos 专用 shrink-to-fit
      （grep 全仓库仅 float/inline-block/table 有 shrink-to-fit，abspos 走 taffy 给 0）。
  (B) flex 替换元素主轴尺寸：即便 (A) 修好给 inner-flex 非零宽，img 在 flex row 容器中
      主轴（宽）默认 = 内容固有（1px），需「cross 轴确定高 + 固有比 → 主轴宽」规则才到 200。
单修 (A) 只能让 inner-flex ~1px（img 固有），img 仍 1x200 ≠ 200x200；须 (A)+(B) 同修。
属「flex 替换元素 definite-size + 固有比」复杂主题（同 Mozilla bug 1469649 谱系），非单点。
裁决：非 clean win，defer（多会话 flex definite-size 架构）。

#2  fixed-table-layout-with-percentage-width-in-flex-item (11.20%)  → 复杂（flex definite-size）
----------------------------------------------------------------
结构：.container(display:flex, width:300) > div（flex item，无显式宽）> .tbl(display:table,
      table-layout:fixed, width:100%, box-sizing:border-box)
期望（chromium / Mozilla bug 1469649）：flex 容器有确定主尺寸 300 → 每个 flex item 含
      width:100% table 后代应得相同确定 post-flex 主尺寸（300/n），table width:100% 解析到它。
ZeroWeb 实测（LAYOUT_DUMP）：
      div.container  w=302（flex 容器，正确）
        div          w=2.0   ← flex item 塌缩到 table 固有（border 2px），应为 ~300
          div.tbl    w=2.0   ← width:100% of 2px
      6 个 container 的 flex item 全部 2px、堆叠在 x=9,11,13...（应均分 300/n）。
      red 背景未被 lightgray table 覆盖 → diff ≈ 6×302×32/480000 ≈ 12%（实测 11.20%）。
根因：flex item 主尺寸（flex-basis:auto）= 内容尺寸；内容是 width:100% table，其固有贡献
      在「flex item 宽不确定」时退化为 min-content（空表 ≈ border 2px）。chromium 把 flex
      容器的确定主尺寸（300）下传让 table 的 width:100% 解析（definite-size resolution）。
属 flex definite-size resolution（同 #1 谱系），非单点。裁决：defer。

#3  multicol-contained-absolute (chromium-Oracle 16.33%, self-source 0.00% = FALSE PASS)
    → 结构性（multicol 单子列平衡）
----------------------------------------------------------------
**首次定位的 false-pass polluted 案根因**（self-source 通过但 chromium 不一致）。
结构：columns:2 > div(position:relative, height:200) > div(overflow:hidden)
      > div(position:absolute, width:100%, height:200, background:green)
self-source ref：columns:2 > div(height:200, background:green)
PIL 像素对比（**纠正 R363 初判「oracle 黑图」= 自写 PNG 解析器 alpha/filter 字节 bug，
              PIL 实测 oracle 内容有效**）：
      ZeroWeb test  绿 x[8,399] y[8,207] = 392x200  （单列、满高）
      ZeroWeb ref   绿 x[8,399] y[8,207] = 392x200  （同 → 同源通过 = 假通过）
      chromium      绿 x[8,791] y[8,107] = 784x100  （满宽 784、半高 100）
根因：multicol `column-fill:balance`（columns:2 默认）应把单个 200px 高子元素平衡到 2 列
      各 100px，green 背景跨两列视觉成 784x100。ZeroWeb 不做「单子列平衡」——把 200px 子
      整个放进列 1（392x200），列 2 空。test/ref 两侧同错故 self-source 假通过。
属 multicol 列平衡 / 碎片化（R113/R131 谱系），结构性。裁决：defer（多会话 multicol 架构）。
**启示**：本类 false-pass polluted 案（self 0% / chr 高）的根因可能是 multicol 平衡而非
      abspos —— 诊断须 PIL 对 oracle，不能只看 self-source。
