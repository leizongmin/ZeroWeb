### 2. IFC vertical_rtl 分支已把 run.x 镜像到右侧

`crates/layout-engine/src/inline/mod.rs:1804-1830`（layout 内，列 x 计算）：
```rust
if self.vertical_rtl {
    // vertical-rl：第一列在右侧，后续列向左排列
    let mut x = self.container_width; // 从容器右端开始
    for col in &mut self.lines {
        x -= col.height; // col.height 在垂直模式表示列宽
        col.y = x;
        for run in &mut col.runs {
            run.x = col.y;   // ← run.x 被设为右侧起始的列 x
        }
    }
} else {
    // vertical-lr：列从左到右，run.x = col.y 从 0 起
    let mut x = 0.0;
    for col in &mut self.lines { col.y = x; x += col.height; for run in &mut col.runs { run.x = col.y; } }
}
```
→ 对 vertical-rl 单列（abspos 静态位置典型场景），`run.x = container_width - col.height`（右侧）。对 vertical-lr，`run.x = 0`（左侧）。**fragment.x 已按 writing-mode 正确定位 block-start 侧**。

## R238 rtl 残余真因候选（read-only 代码推理，须探针实证）

R262 坦诚「mirror 公式纯只读不可定」（三个坐标语义歧义）。本轮代码推理给一个**候选**（未实证确认）：
- **IFC 列 x 基址轴语义错配**：inline/mod.rs:1808 `let mut x = self.container_width`，而 `self.container_width = root.content_width`（engine.rs:1368），engine.rs:1366-1367 注释明确「轴交换后 content_width = 视觉高度（行内方向）」。但 vertical 模式列沿**块轴（=视觉宽度=content_height）**水平排列。故列 x 排列基址用了行内轴尺寸（视觉高）而非块轴尺寸（视觉宽）——对非正方形 CB（如 abs-pos-border-offset-001 的 .cb inline-size:45/block-size:40）会偏。
- 其他候选：border/offset 边处理（.cb 有 `border-width:1px 2px 3px 4px`，静态位置相对 content/padding 边的 writing-mode 边映射）、fragment.width（= col.height）轴语义。
- **探针应问**：dump 某 vertical-rl abspos all-inset-auto 用例的 root.writing_mode / root.content_width / content_height / fragment.x / child.x / chromium 目标视觉 x；若 fragment.x 已 ≈ 右侧（非 ~0），印证 mirror 已生效，残余源于轴基址/border；若 fragment.x ≈ 0，则 IFC vertical_rtl 分支未触达（另案）。**R262 的探针假设「fragment.x 需镜像」须改为「fragment.x 是否已镜像」**。
