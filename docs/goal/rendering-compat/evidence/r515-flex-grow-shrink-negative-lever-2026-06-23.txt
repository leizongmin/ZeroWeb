============================================================
3. ★ 子脉 (b) flex-grow / flex-shrink 负值 = 真实 clean lever（+2 potential）
============================================================

【缺口】apply.rs:577-587 flex-grow/flex-shrink 用 `value.parse::<f64>()` 接受**任意**
f64（含负），直接存 `style.flex_grow = v` / `style.flex_shrink = v`：
```rust
"flex-grow" => { if let Ok(v) = value.parse::<f64>() { style.flex_grow = v; return true; } }
"flex-shrink" => { if let Ok(v) = value.parse::<f64>() { style.flex_shrink = v; return true; } }
```
违反 CSS Flexbox §7.3.1/§7.3.2「negative values are invalid」——负值声明须按未声明处理
→ 留默认 0.0（registry.rs:102 `Number(0.0)`）→ flex item **不 grow/shrink**。
converter/mod.rs:175-176 直接 `style.flex_grow as f32` 传 taffy（负值透传，无 clamp）。

【driving test = genuine upstream WPT，当前 FAIL】
  flex-grow-003.html   标题 "flex-grow - negative number"，assert "set negative number,
                      the flex item will not grow"，用 `flex-grow: -2/-3` → 实测 **1.04% FAIL**
  flex-shrink-002.html 标题 "flex-shrink - number(negative)"，assert "set negative is
                      invalid to shrink"，用 `flex-shrink: -2/-3` → 实测 **3.12% FAIL**
（reftest-upstream single-case，test-guard 包裹，4.94s/case）

【修复 seam（~4 行，apply-time，hand to code agent）】
apply.rs:577-587 加非负守卫：
```rust
"flex-grow" => { if let Ok(v) = value.parse::<f64>() { if v >= 0.0 { style.flex_grow = v; return true; } } }
"flex-shrink" => { if let Ok(v) = value.parse::<f64>() { if v >= 0.0 { style.flex_shrink = v; return true; } } }
```
负值不 set → 保默认 0.0 → item 不 grow/shrink → 趋 ref。**expected +2**（flex-grow-003 + flex-shrink-002）。

【fix cleanliness】driving test 均为**单声明**负值（无 legal-then-illegal 多声明）→ apply-time
拒绝充分（区别 R513c box-model 须 cascade-level）。多声明 edge case（`flex-grow:1;flex-grow:-2`
cascade 选 -2）须 cascade-level（mirror R513c），但无已知 driving test。最小 apply-time 即 +2。
零回归风险：spec 明定负值恒非法，无测试依赖负值被接受。

4. ★ disciplined 排除：column-count 负值非 lever（已正确拒绝）
============================================================

multicol-count-negative-001/002.xht（genuine upstream）当前 **1.17% FAIL**，看似同脉，
但 parse_column_count（parse_extended.rs:598-599）用 `value.parse::<u32>()`（unsigned）+
`if n > 0` —— **负值/0 已在 parse 层正确拒绝**。故 001/002 的 1.17% 失败 = **结构性
multicol**（multicol 23.5% oracle 最低，列分布/balance 精度），**非** 负值接受 bug。
→ column-count **非 lever**（已正确）。教训：f64-parse（flex，signed 接受负）vs
u32-parse（column-count，unsigned 拒绝负）的 parse 类型选择决定是否是 gap，须逐属性核查
parse 路径勿据测试名想当然。
