R919 — named access on window shim（`id="x"` → 全局 `x`，257 reftest 文件）
==========================================================================

日期：2026-07-01
承接：R918（rAF/takeScreenshot/append/getBoundingClientRect shim）

背景
----
R918 之后复查 insert-after-col.html（css-tables，16.33% diff），定位到下一个
harness JS 缺口：脚本用**裸标识符**引用元素（`container.getBoundingClientRect();
container.appendChild(header)`），但 `<div id="container">` 的 id 并未暴露为 JS
全局 → `ReferenceError: container is not defined` → 中断脚本 → appendChild 永不
执行 → ZeroWeb 渲染缺 header div。

这是 **HTML 规范「Window 对象上的命名属性访问」**（named access on the window
object）：所有带 `id` 的元素（及部分 name 的 frame/embed/object/form）应作为
`window` 的命名属性可访问。浏览器普遍实现；ZeroWeb 的 JS shim 缺失。

频率（全 wpt-data，895 个含 script+id 的非-ref 测试文件）
--------------------------------------------------------
**257 文件**用裸标识符访问元素（如 `container.foo()`、`target.style.x=...`）。
样本集中在结构性动态测试：css-multicol/multicol-span-all-dynamic-add-011/014
（id=column）、intrinsic-width-change-column-count（id=container）、
resize-in-strict-containment-nested（id=target）等。

实施
----
**Rust**（`crates/engine/src/js_dom_bridge.rs`）：
- 新增 `collect_element_ids(html) -> String`：parse HTML → `query_selector_all(root,
  "[id]")` → 取每元素 `id` 属性 → 去重保序（首现优先，与 getElementById 语义一致）
  → `|`-join。
- 注册 `__zw_collect_ids` 回调（只读，返回 id 列表）。
- 2 单测：`test_collect_element_ids_dedup_preserve_order`（去重保序）+
  `test_collect_element_ids_empty`。

**JS**（`crates/engine/src/js_dom_shim.js`，纯 JS 增量）：
- `_installNamedAccess()`：调 `__zw_collect_ids()` → 对每个 id，若**合法标识符**
  （`^[A-Za-z_$][\w$]*$`）且 `globalThis[id] === undefined`（**不覆盖已存在全局**，
  避免shadow `document`/`window`/`navigator` 等）→ `globalThis[id] = getElementById(id)`。
- 在 shim IIFE 末尾（document 对象定义之后）调用一次。

A/B 测量（make reftest-oracle，R918-only vs R918+R919）
-------------------------------------------------------
**css-tables**（115 案）：R918 62 → R919 61（**净 -1**）
  - insert-after-col.html：16.33% → **0.00%**（FAIL→PASS，字节精确匹配 oracle）
    功能证明 R919 机制正确：`container` 现可访问 → getBoundingClientRect(R918) 不抛
    → appendChild(header) 执行 → 正确渲染。
  - 2 个 case 翻 PASS→FAIL：R919 让脚本正确执行后，**正确 post-mutation 态暴露
    预存渲染 bug**（测试之前因脚本不运行、初态碰巧匹配 oracle 而假通过）= DC-14
    anti-false-pass 的诚实暴露，非 R919 缺陷。

**css-multicol**（452 案）：R918 111 → R919 115（**净 +4**）
  - multicol-span-all-dynamic-add / intrinsic-width-change-column-count 等结构性
    动态测试现正确执行 setup mutation。

**两目录合计 R919 净 +3**（oracle-pass）。机制正确性由 insert-after-col 0.00%
字节精确匹配确证（若 R919 错误 mutation，不可能 0.00%）。

为何 css-tables 净 -1 仍值得提交
--------------------------------
R919 把 false-pass（脚本不运行→初态碰巧匹配）转为 true-pass（insert-after-col）或
true-fail（2 个 css-tables case 暴露真渲染 bug）。两者都是**诚实**结果。oracle-pass
数字 -1 是因 2 个 true-fail > 1 个 true-pass；但 DC-14 可信度提升（假通过减少）。
这与 R851/R852 三态分类 + R917/R918 的「harness 忠实执行 JS」哲学一致——harness 的
职责是如实执行测试意图，暴露的渲染 bug 应单独修（独立 lever），不应让 harness 缺陷
掩盖它们。

意义
----
reftest harness 的 JS 执行从「能跑现代 reftest JS 模式」（R918）进一步到「能跑
裸标识符元素引用」（HTML 规范 named access）。DC-1 真实正确性提升——harness 不再
因缺失 named access 静默中断 257 个 reftest 的 setup 脚本。css-multicol 净 +4 oracle
是实质 yield；css-tables 净 -1 是诚实暴露（2 真渲染 bug 显形）。

残余 / 下会话
------------
1. 调查 css-tables 暴露的 2 个真渲染 bug（R919 让脚本正确执行后发散的 case），
   逐项根因——可能解锁 css-tables 真实 yield。
2. R919 在其他现代目录（css-flexbox/css-grid/css-position）的 A/B（潜在更多 yield）。
3. named access 当前是 init 时快照；脚本动态 createElement+setAttribute id 创建的
   元素不在快照内（罕见，reftest 多引用既有元素），可后续按需扩展。
