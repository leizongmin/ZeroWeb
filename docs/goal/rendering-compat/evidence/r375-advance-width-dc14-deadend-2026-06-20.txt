2. 该函数被 **layout（IFC 断行 inline/mod.rs:1149 estimate_string_width）+ paint（painter/
   text.rs:559/1082 estimate_char_width for char_x）双侧**调用——改它即 bilateral 一致
   （R225 测的「三处同源」之一，含 intrinsic_sizing）。
3. AdvanceSource trait（text_metrics.rs:68）已定义（R223 plumbing），但**未接线**——
   无任何非 EstimateAdvance 实现，IFC 直接调 estimate_char_width。R223 R2-R5（FontLoader
   注入）未完成。
4. render-foundation/font/shaper.rs:89-110 有 fontdue advance（rustybuzz TextShaper），
   但仅 lib 单测，未接 layout/paint 生产（R331 paint-only net-negative 已证）。
5. R224（DejaVu 表）回退是 **pre-DC-14**（仅 self-source -3，未测 chromium-Oracle）——
   理论上可能是 false-revert（如 R209 被 R355 用 chromium-Oracle 纠正）。

DC-14 实验（已回退）
================================================================
在 estimate_char_width 加 latin_advance_ratio（DejaVu Sans 实测 per-em advance 表：
i=0.279/W=0.939/m=0.879 等，bilateral 影响 layout+paint+intrinsic），测 morning DC-13：

  morning z_vs_chr（product-smoke 阈值0）：
    R373（0.55 启发式）: 16.41%
    R375（DejaVu 表）  : **19.14%（+2.7pp 退步！）**

================================================================
结论 1：advance-width 非 morning cascade 根因（R374 推断证伪）
================================================================
若 cascade 是 advance-width，精确 advance 应改善 morning。实测反而 +2.7pp 退步 → cascade
**非 advance-width**。R374 的「换行级联 = advance-width」推断**错误**，已纠正。

================================================================
结论 2：morning cascade 是**字体不匹配**（非 advance 计算错误）
================================================================
机制：morning 用 `font-family: system-ui`（chromium 用 OS 系统 UI 字体，如 Linux 的
Sans/Firefox Sans）。ZeroWeb fontdue 用**捆绑字体**（非 OS system-ui）。DejaVu 表是第三种
字体的度量。三者（crude 0.55 启发式 / DejaVu 表 / chromium 实际 system-ui）中：
  - crude 0.55「所有字母等宽」**碰巧接近 system-ui 的平均字宽** → morning 16.41%
  - DejaVu per-char 表与 system-ui 的 per-char 分布**不同** → 换行点偏离 system-ui 更多 → 19.14%
即 advance-width 改善须用**chromium 实际字体的 advance**（OS system-ui），而 ZeroWeb 无该字体
（fontdue 捆绑字体≠system-ui）。故 advance-width 在当前字体栈下**不可修**——是字体加载/匹配
问题（须加载与 chromium 相同的 system-ui 字体），非 advance 计算问题。

================================================================
结论 3：advance-width lever DC-14 终局关闭（强化 R225）
================================================================
R225「reftest-oracle 26 case 零变化」+ 本轮「morning DC-13 +2.7pp 退步」= advance-width
bilateral 改善在 DC-14 真值上对 Ahem（reftest）零变化、对非 Ahem（morning）负向。**R224 回退
非 false-revert**——accurate advance 确实不帮助（与 R209 不同，R209 是 self-source 假阴性而
chromium-Oracle 真改善；advance-width 是 chromium-Oracle 真退步）。**advance-width lever
DC-14 终局关闭，勿再以任何变体（静态表/FontLoader/shaper 接线）重试**——根因是字体不匹配，
非 advance 计算。

================================================================
启示：morning cascade 下一步方向（非 advance-width）
================================================================
morning 16.41% cascade 既非 advance-width，则候选 = **line-height**（fontdue line metric≠
Skia）或 **glyph 渲染**（fontdue AA/度量≠Skia，DC-14 line 311 说 AA 基本一致，但 line metric
可能差）。二者均 fontdue vs Skia 字体层差异，非布局 bug，须字体光栅器升级（多会话/架构）。
**勿再以 morning cascade 为单会话 layout 杠杆**——已证非 advance-width，剩余是字体层。

================================================================
更正（同轮，重要）：R375 hand-crafted 表是**不准确代理**，结论应降为 inconclusive
================================================================
后续核查发现：① ZeroWeb fontdue 加载系统字体 /usr/share/fonts/truetype/dejavu/DejaVuSans.ttf
（loader.rs:467），即 fontdue 用 DejaVuSans；② R375 的 latin_advance_ratio 表是我**手写近似**
（i=0.279/W=0.939 等是我估的 DejaVu 比率，非从 DejaVuSans.ttf 实测），与 DejaVuSans 真实
advance 有偏差。故 R375 morning +2.7pp 退步**可能来自表不准确**（非 advance-width 真死），
结论应从「终局关闭」**降为 inconclusive**。

fontdue **实际 advance** 测试（用 measure_advance / font.metrics 的真实 DejaVuSans 值）才是
definitive test，但本轮未做——障碍：① measure_advance 调 rasterize_glyph_with_fallback 会
**rasterize**（paint 导向，layout 热循环太慢）；② fontdue 非 layout-engine 直接依赖（须加 dep
或用 render-foundation FontLoader 穿引用）；③ estimate_char_width 是无状态自由函数，须穿
font context（AdvanceSource 接线，R223 R2-R5 Phase A）。故 fontdue-actual 变体**未 definitive
证伪**。

【诚实裁决】advance-width lever 的**preponderance of evidence**（R224 实测表 -3 / R225 oracle
26案零变化 / R320 双侧 estimate 一致 / R331 paint-only net-neg / R375 hand-crafted 表退步）
指向**非 clean win**，但**非 definitive 关闭**——fontdue-actual（Phase A 接线）是唯一未测变体。
勿以 R375 为「彻底关闭」依据拒绝未来 Phase A 的 fontdue-actual 测试；亦勿在 Phase A 就绪前
以单会话重试（静态表/hand-crafted 已证不奏效）。

R375b definitive：fontdue-actual advance 亦退步 → advance-width 终局关闭
================================================================
为消除上面「hand-crafted 表不准确→inconclusive」的疑虑，做 fontdue-actual definitive test：
临时给 layout-engine 加 fontdue dep，在 text_metrics.rs 加 default_fontdue_font()（OnceLock
缓存，读 /usr/share/fonts/truetype/dejavu/DejaVuSans.ttf = ZeroWeb 实际加载的字体），estimate_char_width
对 ASCII 用 font.metrics(c, font_size).advance_width（raw metric，无 rasterize，cheap）。

  morning z_vs_chr：R375b（fontdue-actual DejaVuSans advance）= **19.08%**
  对比 R375（hand-crafted 表）= 19.14%，R373（0.55 启发式）= 16.41%

fontdue-actual（19.08%）≈ hand-crafted（19.14%）≈ 均比 16.41% 退步 ~2.7pp。**R375 hand-crafted
表是准确的**（与 fontdue-actual 一致），上面「inconclusive」更正**过度谨慎**——R375 结论成立。

【definitive 裁决】advance-width bilateral 改善（无论 hand-crafted 表 / fontdue 真实 advance）
在 DC-14 上**均使 morning 退步**（~+2.7pp）。机制：accurate DejaVuSans advance 使 ZeroWeb 换行
偏离 chromium——chromium 的 system-ui 字体 ≠ DejaVuSans（尽管 AA 基准 glyph 形似），或 chromium
换行算法不同；crude 0.55「所有字母等宽」启发式**碰巧更接近 chromium 的换行**。故 advance-width
**非** morning cascade 根因，cascade 是 line-height / glyph-rendering / 字体不匹配（chromium 实际
system-ui 字体层）。

advance-width lever **definitive 终局关闭**（R375b fontdue-actual 是最后未测变体，亦证伪）。
勿再以任何变体（hand-crafted 表 / fontdue-actual / FontLoader 接线 / shaper）重试 advance-width。
R375b 已回退（移除 fontdue dep + text_metrics 还原，morning 恢复 16.41%）。
