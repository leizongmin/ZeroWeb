1. R515 声称什么（被本轮证伪）
============================================================

R515 §3-§6 声称：
- apply.rs:577-587 flex-grow/flex-shrink 用 `value.parse::<f64>()` 接受任意 f64（含负），
  违反 CSS Flexbox §7.3.1/§7.3.2「negative values are invalid」。
- 负值透传 taffy → item 错误 grow/shrink → flex-grow-003 / flex-shrink-002 FAIL。
- R515 §6「de-risk 复核」读 vendored taffy flexbox.rs，**声称** taffy 不 clamp 负 flex_grow：
    flexbox.rs:1271  `if growing && sum_flex_grow > 0.0`
  R515 据此断言「负值进 sum_flex_grow → 影响 grow 分布 → item 尺寸错」→ +2 yield 经代码核查坐实。

============================================================
3. ★ R515 §6 对 taffy 的代码阅读 = 误读（真机制）
============================================================

R515 §6 引用 `flexbox.rs:1271 if growing && sum_flex_grow > 0.0` 并断言「负值进 sum
→ 影响 grow 分布」。但该行是 **GATE（门控）**：sum_flex_grow > 0 为假（负和）→
growing 分支不执行 → **items 不 grow**。即 taffy 运行时已把负 flex-grow 当作 no-grow。

运行时 primitives 实证（test1/test2 = 25px，未 grow）**直接证实**：负 flex-grow(-2/-3)
在 ZeroWeb 当前（无 R515 fix）下已产生 no-growth 行为，等价于 flex-grow:0。
→ apply.rs 是否拒绝负值对最终布局**零影响**（taffy 已在 sum>0 门控处等效处理）。

R515 §6 把「负值不被 clamp」误推为「负值影响分布」，忽略了 `sum > 0` 门控使负和短路
no-growth。**confidence 从「代码核查确证」纠正为「代码阅读误推 + 运行时证伪」**。

教训（强化 R515 §4 column-count 教训）：taffy 行为的代码推断须用 LAYOUT_DUMP/primitives
**运行时实证**，不能据单行代码 + 推理链定论（R515 §6 即犯此错）。

4. flex-grow-003 / flex-shrink-002 的真实失败根因（新 lead）
============================================================

flex-grow-003 真实 5000px diff = test1(25×100=2500) + test2(25×100=2500) RED box 可见。
预期（CSS Appendix E）：#cover（position:relative green 50×100，body 第三子，前两个是
p + #container）应绘于 #container 的 in-flow flex items（test1/test2，step 5）**之后**
（#cover 是 positioned，step 6）→ 覆盖 red → 全绿。但 red 可见 = #cover 未覆盖。

DO_DEBUG 实证 draw_order Fill 序列（render-foundation/cpu/mod.rs render_draw_order，
zero-wpt-runner reftest-upstream flex-grow-003）：
  DO[46] Fill(0) container green (8,51,100,100)
  DO[47] Fill(1) cover    green (8,51,50,100)   ← step 6 positioned
  DO[48] Fill(2) test1    red    (8,51,25,100)   ← in-flow flex item (step 5)
  DO[49] Fill(3) test2    red    (33,51,25,100)

→ **#cover 绘于 test1/test2 之前**（违反 Appendix E：positioned step 6 应在 in-flow step 5
之后）。draw_order push 顺序 = paint_node DFS 顺序（cull_invisible 仅重映射索引不重排，
已核查 ops.rs:490-509 filter_map 保序）。

layout tree 结构（LAYOUT_DUMP）确认无异常：
  div #container (w=100)
    div #test1 (w=25)
    div #test2 (w=25)
  div #cover (w=50)   ← #container 的兄弟，body 直接子
→ test1/test2 确为 #container 子节点，#cover 是其兄弟。结构正确。

★ 根因未完全定位（painter scope/collect/flush 逻辑）：按 paint_node 主循环（painter/mod.rs
657-686）+ collect_positioned_descendants（150-192）+ engine.rs creates_stacking_context
（739-741：仅 positioned+z-index:Integer 或 opacity<1）的代码 trace，#cover 应被 html/body
root scope 收集到 step 6、绘于 step 3-5（含 #container 子树 test1/test2）之后 = 最后。
但 draw_order 实证显示 #cover 在 test1/test2 之前。trace 与实证矛盾，疑点：
  (a) is_relative flag 是否真为 #cover 置位（若否，#cover 留在 step 3-5 tree-order，
      应在 #container 子树之后 = red 被覆盖 = PASS，与实测 FAIL 矛盾）；
  (b) root scope 是 html 还是 body / collect 是否真收集 #cover；
  (c) 是否存在未发现的 flex-item 延迟绘制路径。
需 runtime 插桩 is_relative + scope 收集顺序（多会话 painter 调试，R503/R504 territory）。

flex-shrink-002 同类：15000px = test1 red 未被 cover 完全覆盖(5000) + test2 green overflow
到 ref 白区(10000)。flex overflow 布局 + cover paint-order 双重，结构性。
