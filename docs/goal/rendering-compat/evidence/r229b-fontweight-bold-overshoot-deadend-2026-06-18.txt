# R229 font-weight 落地实测：bold 选择机制正确但 fontdue 粗体渲染过墨 → net-negative 死路（已回退）

**日期**: 2026-06-18
**模式**: 实现 + 实测后回退（代码已 git checkout 回 HEAD，基线 438/490 持平）
**承接**: R229（font-weight 未落地精确方案）/ R230（资源前提实证）

## 实现（已回退）

完整落地 R229 两部分方案：

**B 接线（render-foundation + engine）**：
- `FontLoader`：`load_font` 解析 OS/2 `usWeightClass` 存 `font_weights: HashMap<u32,u16>`；`find()` 按 CSS Fonts §5.2 最近字重选变体；新增 `FontResolveEntry { variants: Vec<(u16,u32)> }` + `pick(target)`；`build_font_resolver()` 返回 `HashMap<String, FontResolveEntry>`。
- `pipeline.rs` + `painter/mod.rs`：resolver 类型升级；`resolve_font_id(font_family, font_weight)` 按 `FontWeightValue` 取目标字重（Bold=700/Normal=400/Absolute(n)=n/Bolder≈700/Lighter≈400）。
- `painter/text.rs`(5) + `effects.rs`(1)：6 处 `resolve_font_id(&style.font_family, &style.font_weight)`。
- workspace 全量 build 干净（类型经 `set_font_resolver(build_font_resolver())` 自动流转 ~20 调用点）。

**A 资源**：`app_platform.rs::load_system_fonts` + `reftest.rs::create_font_loader` 加载 `DejaVuSans-Bold.ttf` / `NotoSans-Bold.ttf` / `LiberationSans-Bold.ttf` / `NotoSansCJK-Bold.ttc`（系统已装，R230 实证）。

## 实测结果：机制正确但渲染过墨 → net-negative

粗体**确实被选择并渲染**（welcome card h3 区 ink-mass old-ZW 2095 → new-R229 **2713**，+29%，证明 font-weight 接线生效）。但 fontdue 光栅化的 `DejaVuSans-Bold` 比 chromium 的 bold **过墨 ~15%**：

| 区域 | old-ZW | new-R229 | chromium | 判定 |
|------|--------|----------|----------|------|
| title/eyebrow (y=20-90) | 1458 | 1559 | **1363** | new 过墨 +14% |
| cards h3 (y=240-390) | 2095 | 2713 | **2318** | new 过墨 +17% |

→ welcome product-smoke（800×600）**17.06% → 17.55%（+0.49pp 回归）**；morning-work full-page 48.65% 不变（其 h1-h6 显式 weight:400，仅 `<strong>/<b>` weight:600 故影响小）。按项目零回归标准 = net-negative，**已回退全部代码**。

## 死路定性（纠正 R229「welcome 17% 主因=font-weight」假设）

R229 据 CSS-weight × ink-mass 断「bold 欠墨是 welcome 17% 主因」。实测后**部分证伪**：
- bold 接线**确实让粗体文本加墨**（card h3 +29%），方向正确；
- 但 fontdue 对 DejaVuSans-Bold 的光栅化**过墨 ~15%**（非欠墨），与 chromium 的 bold（FreeType+Skia 子像素渲染）不可像素对齐——**同 advance-width(R225)/AA(R174) 谱系的 fontdue-vs-chromium 渲染差异**，非「字重未选」可单点修复。
- 且 bold 变体的 advance width 与 Regular 不同 → 粗体标题换行/位置偏移 → 级联布局差，进一步增 diff。

**结论**：font-weight 接线是**正确且自源中性**的基础设施（reftest 438 不变，Ahem 无 weight），但**加载粗体资源后对产品 smoke net-negative**（fontdue 粗体过墨 + advance 级联）。保留接线需搭配 fontdue 渲染校准或与 chromium 同字体选择，**非单会话可成**。勿再以「加载 DejaVuSans-Bold 接线」重试 R229——会重现过墨回归。

## 残余 welcome 17% / morning-work 48.65% 真因（重新定性）

font-weight 非主因后，残余主因：
- **item-tag span→block 全宽堆叠**（R109 IFC inline→block 架构，welcome/morning-work 顶部蓝色全宽条）
- **fontdue vs chromium 字体度量噪声**（CJK line-height/advance，非 weight）
- **morning-work**: hljs 语法高亮缺失（需 JS）、body 高度 ~300px 差
- 均已知独立子问题，非 font-weight 单点可解。

无代码变更（实验已 git checkout 回 a2b169e），基线 438/490 持平。
