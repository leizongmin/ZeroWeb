# R975 RFC Phase 0 Probe Report — vertical-align-117a (linebox-metric-rfc §4.3)

Date: 2026-07-03
Test: css/CSS2/linebox/vertical-align-117a.xht
  div { font: 2.5em/3.25 Ahem; background: yellow; }   # 40px/130px, half-leading 45px
  span { color: blue; vertical-align: text-bottom; margin: auto -1em; }
  <div>TTTT<span>MustBeAbove</span>TTTT</div>
Expectation: blue span entirely ABOVE black TTTT stripes.

## Method
Env-gated eprintln probe in `apply_vertical_alignment` (crates/layout-engine/src/inline/mod.rs:1651),
run via `RFC_PHASE0=1 ... reftest-upstream vertical-align-117a`. Probe removed after capture.

## Layout-side measurements (the 117a span line)
  line.height      = 130.00   (= 3.25 × 40, line-height inherited) ✓
  strut_ascent     = 77.00    (= (130-40)/2 + 40×0.8 = 45 + 32, R800 half-leading formula) ✓
  baseline_y       = 77.00
  run.fs (span)    = 40.00    (2.5em Ahem)
  run.height (span)= 130.00   (span inline-box height = inherited line-height; per CSS §10.8.1
                               the box used for vertical-align IS the line-height box) ✓
  run.va           = TextBottom

## Code formula (inline/mod.rs:1665)
  VerticalAlignValue::Bottom | VerticalAlignValue::TextBottom => line_height - run.height
  → for 117a: run.y = 130 - 130 = 0   (span box bottom = 0 + 130 = 130 = LINE-BOX bottom)

## Spec-correct text-bottom (CSS §10.8.1 / visudet.html#leading)
  text-bottom aligns the span box bottom with the PARENT's CONTENT-AREA bottom
  (= baseline_y + font-descent; excludes half-leading — distinct from `bottom`
  which uses the line-box bottom).
  Parent content-area bottom = baseline_y + descent ≈ 77 + 0.2×40 = 85
  → spec run.y = 85 - 130 = -45   (span box bottom = 85 = content-area bottom)

## Findings
1. **Layout formula deviation CONFIRMED**: code treats TextBottom == Bottom
   (line 1665 collapses both arms to `line_height - run.height`). Spec requires
   TextBottom = parent content-area bottom (baseline_y + descent), Bottom = line-box
   bottom. For 117a the difference is 130 vs 85 → run.y 0 vs -45 (45px off).
2. **Paint-dead (R949 re-confirmed via different angle)**: R949 empirically showed
   vertical-align on/off = 117a unchanged (13.59% both). So fixing the layout
   formula ALONE will not yield oracle improvement — paint Path A (stored) does not
   consume run.y for Ahem containers. This is the Phase-A double-path deadlock:
   layout computes a (here also wrong) run.y, paint ignores it.

## Contract for Phase 1 (per RFC §4.3)
Phase 1 must do BOTH, in one change, to yield:
  (a) layout: split TextBottom arm from Bottom — run.y = (baseline_y + descent) - run.height,
      where descent = font descent metric (Ahem ≈ 0.2em; real font = fontdue descent).
  (b) paint: make Path A consume the stored run.y (currently dead) for stored containers.
Doing (a) alone = R949 no-yield; doing (b) alone without correct (a) = wrong position.
This is the "three-way change, not single-point" requirement (R876) — confirmed by probe.

## Verdict
Probe establishes the precise contract the RFC required before any code change.
Confirms the deadlock is real and structural (Phase-A unification, multi-session).
Single-session slice on 117a alone is NOT viable (paint-dead). This round = read-only
data gathering, zero net source change (probe added then removed).
