## 范围

s24 挂账「corner-cases hang（余 ~28 案被 file Timeout 吞没）」。一个横切

Timeout。诊断链另纠正 s23 的错误归因（「detach 窗口身份链」不成立）。

## 根因链（两层机制）

1. **shim**（part04.js 三处重复 `close` 包装）：`return
   _zwDialogClose(...)` 透传 helper 的 `wasOpen` boolean。spec
   `close(returnValue)` 为 void（返 undefined）。
2. **语料 testharness（正确行为，非 runner 缺口）**：
   - `is_valid_cleanup_result`——cleanup 回调须返 `undefined`
     （promise_test 可返 thenable）；boolean → `bad_value_count` →
     `tests.abort()`。
   - `Test.prototype.cleanup` 的 `on_error`——cleanup **抛错**同样
     `tests.abort()`（源码注释 "Abort tests immediately"）。
   - `tests.abort()` → 完成回调永不被调 → runner 合成 file Timeout；
     partial_results 照常上报、余案全吞。

即 `t.add_cleanup(() => dialog.close())` 返 `false` 一个值吞掉整文件。
全部受害文件首案都走 light dismiss/close 请求（cleanup close 已关 dialog
→ 返 false → abort）。

## 诊断路径（探针页五文件）

file Timeout 形态学（partial results 仅首案 + 余案全无）→ 每步独立
promise_test 探针（partial flush 定位断点）→ C 探针：C1（cleanup 含
close）Pass 后 C2（纯 `outside.focus()` 同步案）不运行 → 断链在 C1 完成
后的 harness 微任务链 → cleanup 唯一内容 close() → DA/DB 对照（cleanup
空操作 / body 内 close 均全绿）锁定 cleanup 路径 → 读语料
`is_valid_cleanup_result` 落根因。s23 的「ESC modal 案 awaitClose 不达 /
detach 窗口身份链」归因作废：hang 案实为「前一案 cleanup abort」，
awaitClose 机制本身无恙（ESC 面首案翻绿已证）。
