## webapi streaming 簇收敛（27F → 2F）

五处修改，全在 runner 面（`tests/wpt-runner/src/testharness.rs` 预热回挂点 +
fetch 静态服务路径；`tests/wpt-runner/scripts/goals/32-wasm-compat.sh` 语料补拉），
生产 engine 路径不动：

1. **静态 `.wasm` MIME**：`wpt_static_resource_headers` 补 `.wasm →
   application/wasm`（照上游 wptserve mime.types）——contenttype 合法 MIME 腿经
   fetch 静态读断言 compileStreaming 成功的前提。
2. **同名头去重保首项（pipe 优先）**：pipe 头与默认 MIME 并存时页面
   `Headers.get` 按 HTTP 组合语义逗号拼接（`application/wasm, application/wasm`
   → 整值判定误挂）。去重与 wptserve `pipe=header()` 替换语义及 CT 解析侧
   「首项胜出」同向。
3. **streaming 两件入参 Promise<Response>**：spec 一等支持——await 后对
   resolved 值做 Response 鸭子检查；入参 promise 的 rejection 原样传播
   （abort.any.js 的 AbortError / rejected-arg.any.js 的自定义 error 不得被
   换型成 TypeError）。
4. **Content-Type 整值判定**：`trim().toLowerCase() !== 'application/wasm'`
   即拒——上游 contenttype.any.js `invalidContentTypes` 钉死
   `application/wasm;charset=UTF-8` / `application/wasm;` 均 invalid，非 MIME
   essence 剥离（旧实现的 `split(';')[0]` 误放行参数形态）。
5. **Module 不可序列化**：`__zwRegisterNonCloneableProto(W.Module.prototype)`
   登记进 shim 平台对象拒绝注册表——structured clone / IDB `store.put(Module)`
   抛 DataCloneError（historical.any.js；JS-API：Module 无序列化槽位）。
6. **语料补拉**：顶层 `wasm/incrementer.wasm` 单点补拉（webapi 集成面绝对
   `/wasm/incrementer.wasm` 与相对 `../incrementer.wasm` 引用都落此路径；DIRS
   深挖不覆盖顶层散文件）。

收敛明细：contenttype 6F + abort 6F + body 2F + empty-body 4F + rejected-arg 2F
+ wasm_stream_compile 3F + wasm_stream_instantiate 3F + historical 1F = 25F。

**残差 2F 挂账**（`wasm_stream_compile/instantiate_test.any.js` :: using
ReadableStream with ArrayBuffer chunk）：Response 体流 enqueue **非**
ArrayBufferView 的 chunk（裸 ArrayBuffer）须 TypeError 拒——engine streams
体消费读循环的 chunk 类型门（streams spec read-loop / fetch body 语义）。
属 net-api goal 域（streams corpus 同面），不越共享面（engine 此刻有并行流
未提交 WIP，run-rules §9 碰头信号规则）。

## memory64 簇定性翻案（9F：引擎缺口 → Chrome 同形）

M1/M2 定性「V8 proposal 门控语义差，挂账 M3 flag 实验」**证伪**，两处修正：

- **门控半边不存在**：runner V8（rusty-v8 150.2.0）二进制内无
  `experimental_wasm_memory64` flag 字符串（shipped 特性无 flag）——memory64
  语法已启用。探针实证（scratch 页 `wasm/webapi/mini/d-memory64-probe.html`，
  收口前已删）：`validate` 对 memory64.wast:8/9、table64.wast:9 三模块均
  false；`new Module` 报 `initial memory size (281474976710656 pages) is
  larger than implementation limit (262144 pages)`——解析面认得 64 位 flags，
  拒点是 **V8 16GB（2^18 页）memory64/table64 声明上限的 validation 期检查**
  （kMaxMemory64Size）。
- **浏览器同形实证**（wpt.fyi aligned stable 07ce6e987a，chrome
  156.0.8078.73，`tests/wpt-runner/wptfyi-cache/summary-chrome.json`）：

  | 文件 | chrome stable | 本轮 ZW |
  |---|---|---|
  | `memory64/memory64.wast.js.html` | 102/107（5F） | 5F |
  | `memory64/table64.wast.js.html` | 39/41（2F） | 2F |
  | `table.wast.js.html` | 102/104（2F） | 2F |

  失败计数逐文件相等（9F），同一 V8 血统同形。M1 对失败形态的解读亦勘误：
  `assert_equals: expected false but got true` 是 WPT `assert_equals(actual,
  expected)` 消息序——harness（EXPECT_INVALID=false，期待模块合法）期望
  `validate=true`，环境判 false；非「环境判 true」。

**处置**：挂账销账——定性为「上游 spec 套件超出 V8 系实现声明上限
（Chrome 同形）」，不修、不计引擎缺口；后续 V8 若放宽 kMaxMemory64Size 声明
检查（或语料 pin 前移引入实现上限差异），随 drift 巡检重估。
