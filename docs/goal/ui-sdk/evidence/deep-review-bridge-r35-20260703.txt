修复 A（潜在 correctness，已修）：glyph_cache_key FontId 位打包碰撞
----------------------------------------------------------------------
- `FontId(pub u32)`（foundation/text/src/font_request.rs:10），但旧 `glyph_cache_key`:
    ImageKey(((font_id.0 as u64) << 48) | (((glyph_id) & 0xFFFF_FFFF) << 16) | size_q2)
  `font_id << 48` 把 u32 放进 bits 48-63（仅 16 位）→ FontId 高 16 位（bits 16-31）丢失。
- 后果：FontId ≥ 65536 且低 16 位相同的字体 → 同一 cache key → 取错 glyph 位图（视觉损坏）。
- 实际影响：FontId 顺序分配自 0，浏览器约 5-20 字体，实践中难达 65k → 潜在、非现行 bug。
  但位打包对 FontId 的 u32 契约不正确（与 DC-11 深度审查修 glyph_id u32→u16 截断同性质）。
- 修复：位重分配 font_id bits 32-63 / glyph_id bits 16-31 / size bits 0-15。
  glyph_id 经 foundation/text shape_with_font 钳制 ≤ u16::MAX（DC-11 M2 修复），故 & 0xFFFF 无损；
  三者占满 u64，全 FontId u32 范围无碰撞。
- 回归守卫：`glyph_cache_key_distinguishes_font_ids_beyond_u16`（FontId(1) vs FontId(65537)
  vs FontId(u32::MAX) 必区分；旧代码此测会 FAIL）。

文档化 B（潜在设计假设，加注释不改逻辑）：raster_runs 单 run 假设
----------------------------------------------------------------------
- `raster_runs` 每 run 内 pen_x 自 0 起累进。foundation/text `shape()` 当前产出**单个** GlyphRun
  （backend.rs:189 `vec![GlyphRun]`），故正确。
- 若未来引入字体 fallback 产出多 run，本函数需跨 run 累计 pen_x（GlyphRun 当前无 run-level
  起点偏移字段）→ 否则各 run 重叠在 position.x。
- 处置：加注释文档化单 run 假设 + 多 run 所需的 ShapedText/GlyphRun 扩展，不改逻辑（避免
  对不存在的多 run 场景做投机性未测代码；shaper 单 run 时任何 pen_x 移动都是 no-op）。
