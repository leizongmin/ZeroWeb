## 关键发现：SDK chrome 布局 bug（chrome diff 真正主因）

chrome 区 diff 74.40% → **74.05%**（-0.35pp，颜色 parity 影响微小）。诊断发现**真正主因是 SDK chrome
布局 bug**：dump sdk_prims.fills 仅 **2 条**：

1. `(0,0,1280,40)` — tab strip（column 首子，正确布局）。
2. `(0,80,154,4)` — nav widget 节点 rect **高 4**（应为 `(0,40,154,44)`）！

toolbar 行（nav/address/security/menu）与 bookmarks bar 的 fill **完全缺失**。即 host 布局把
toolbar 容器（ROW）及其子节点、bookmarks leaf 的高度算错（nav 节点得 4px 而非 44px；其余子节点 0px）。
只有 column 首子（tab strip）布局正确。

像素采样佐证：SDK fb 在 toolbar 区（y=40-80）全白（255，无 fill），bookmarks 区（y=84-112）全白；
只有 tab strip（y=10-30）渲染了 SDK fill（230）。手绘同区都是 toolbar_bg(248)。

**结论**：颜色 parity + 图标 + fresh-tab fallback 都是正确的基础工作，但**在布局 bug 修好前不可见**
（toolbar/bookmarks fill 不渲染）。布局 bug 是 chrome diff 的真正阻塞，修好后预期 diff 大幅下降
（toolbar+bookmarks 占 chrome 区大半像素）。

## 下轮下一步（chrome diff 真正阻塞 = 布局 bug）

定位 host（ui/runtime/host.rs）column/row 布局为何把 toolbar 容器子节点高度算错（nav 得 4px、
address/security/menu/bookmarks 得 0px），只有 column 首子（tab strip）正确。怀疑：column 对容器
子节点（ROW）的 measure/arrange 递归，或 constraints 向 row 子节点传播时 cross-axis（高度）被压缩。
修好布局后 toolbar/bookmarks fill 渲染，颜色 parity + 图标生效，重测 dc14_chrome_region_pixel_diff_baseline
看 chrome 区 74.05% 大幅下降。
