## 发现 1：pump_frame layout-only 失效漏 paint（medium，已修复）

- **位置**：ui/adapters/winit/src/driver.rs pump_frame（修复前）
- **严重程度**：中（潜在 correctness，当前 driver setter 未触发但 API 可达）
- **置信度**：0.85
- **描述**：pump_frame 此前先 `if needs_layout() { layout() }`（layout 清除 NEEDS_LAYOUT），
  **之后**才 `if needs_paint()`。requires_paint() = NEEDS_LAYOUT || NEEDS_PAINT；layout 已
  清除 NEEDS_LAYOUT → 若 pending 原本仅 NEEDS_LAYOUT（无 NEEDS_PAINT 位），paint 被跳过。
  layout 改了几何但 scene 不刷新 → 停留旧帧。
- **触发条件**：pending = NEEDS_LAYOUT 单独。经公开 `WidgetHost::mark(NEEDS_LAYOUT)` 可达；
  或某 widget 经 `ctx.invalidation |= NEEDS_LAYOUT`（不伴 NEEDS_PAINT）。当前 driver 的
  setter（set_metrics/set_tokens/begin/set_root reconcile）都同时标 NEEDS_PAINT，故未触发；
  但 pump_frame 契约应对单独 NEEDS_LAYOUT 鲁棒（layout 隐含 repaint，见 invalidation.rs
  注释「layout 隐含需要 re-paint」）。
- **代码证据**：
  ```rust
  // 修复前
  if self.host.needs_layout() { self.host.layout(...); }  // 清除 NEEDS_LAYOUT
  if self.host.needs_paint() { ... }  // 此时 requires_paint 可能已假 → 漏 paint
  ```
- **修复**：layout 前捕获 `let should_paint = self.host.needs_paint();`（NEEDS_LAYOUT 仍在 →
  requires_paint 真），layout 后按捕获决策 paint。
  ```rust
  let should_paint = self.host.needs_paint();
  if self.host.needs_layout() { self.host.layout(...); }
  if should_paint { self.host.paint(); Repainted } else { Idle }
  ```
- **回归守卫**：`pump_frame_paints_when_only_needs_layout_marked`——host.mark(NEEDS_LAYOUT)
  单独失效 → 断言 pump_frame 返回 Repainted（旧实现返回 Idle = 漏 paint，测试会失败）。
- **验证状态**：✅ 确认（逻辑推演 + 测试；winit 30→31 测全绿）。

## 发现 2–5：low / 非 bug（记录，不修）

### 发现 2：set_metrics 不自动重派生 theme typography（low，非 bug — 设计边界）
- **位置**：driver.rs set_metrics。
- **描述**：set_metrics 更新 metrics + 标 needs_layout，但不重派生 TypographyTokens/SpacingTokens
  （text_scale/density 影响）。driver 仅持 SemanticTokens（色）；TypographyTokens 不在 driver
  状态里（host 也不直接消费——widgets 用各自 sizing 启发式）。
- **结论**：非 bug，是「driver 不集成 ThemeProvider」的设计边界（master.md 已记 ThemeProvider
  集成为 follow-up）。caller 责任在 metrics 变时另调 set_tokens 派生新 token。文档化即可。

### 发现 3：pump_event 在 Handled 但状态未变时仍重建（low，wasteful 非错误）
- **位置**：driver.rs pump_event `if handled { set_root }`。
- **描述**：app.dispatch 返回 Handled 但实际未改状态时，root_spec 重建出等价 spec → reconcile
  no-op（props 不变）但仍标 NEEDS_PAINT|SEMANTICS。一次多余重绘。
- **结论**：wasteful 非错误；reconcile 廉价（稳定 WidgetId 复用）。Flutter setState 同模式。
  不修（修需 UiApp 暴露「状态是否真变」信号，过度设计）。

### 发现 4：begin 非幂等守卫（low，无害）
- **位置**：driver.rs begin。
- **描述**：重复调 begin 会再 reconcile + layout + paint（重渲染首帧）。
- **结论**：无害（idempotent 结果）；caller 不应重复调。不修（加守卫属过度防御）。

### 发现 5：pump_event 后未 pump_frame 读 scene 得旧帧（low，契约文档化）
- **位置**：driver.rs pump_event（不 paint，仅 set_root reconcile）。
- **描述**：pump_event 处理事件 + 可能重建，但不 paint（两阶段：事件→帧）。caller 若在
  pump_event 后、pump_frame 前读 host.scene()，得上一帧 scene。
- **结论**：刻意两阶段设计（事件处理与渲染分离，类游戏 loop）；EventOutcome.needs_redraw
  信号何时需 pump_frame。文档已说明（「每帧调 pump_frame + host.scene() 喂渲染桥」）。非 bug。
